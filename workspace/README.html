사용자 감독형
개발 워크벤치

에이전트가 흐름을 통제하는 것이 아니라 사용자가 통제하는 데스크톱 환경. 모든 side effect는 approval → runner → evidence → quality gate를 거친다. Electron · React · SQLite WAL, 서버 없이 로컬에서만 동작.

01HarnessAgentOS 는 무엇인가

LLM 에이전트와 함께 일하되, "에이전트가 알아서 처리" 가 아니라 "사람이 매 단계를 감독" 하는 워크벤치. BLOCK FLOOR · approval-first · evidence-based 라는 세 가지 원칙이 코드 레벨에서 강제된다.

Approval-first

파일 쓰기, shell, git commit, network 등 모든 side effect는 사용자 승인 없이 실행되지 않는다. 자동 승인을 켜더라도 BLOCK FLOOR(profile blocked action)는 항상 우선.

Evidence-based

실행된 모든 action은 artifact(plan, diff, stdout, test report)를 남긴다. markDone은 passed/warning QualityGate가 있어야 호출된다.

Pre-execution budget

Agent Profile에 USD 한도를 두면 추정 비용 초과 시 자동 승인이 budget 단계에서 차단된다. 사후 기록이 아닌 사전 게이트.

Decision trace

모든 자동 승인 결정은 7단계 결정 흐름과 사유가 approval row에 영구 저장되고 UI 토글로 확인 가능.

03핵심 개념

실행 흐름

사용자 입력 → Thread → TaskRun → Step → Checkpoint
            → Approval → Runner → Artifact → QualityGate → Done
  • Thread: 관련 작업 묶음 단위. target directory와 default pipeline을 기억.
  • TaskRun: 단일 요청. 9가지 상태(drafting, waiting_for_approval, running, paused, blocked, quality_failed, ready_for_review, done, cancelled) 사이를 전이.
  • Approval: 모든 side effect의 게이트. 9가지 action type(file_write, shell, git_commit, network, capability_use, model_use, dependency_install, skill_script, orchestration_plan).
  • Artifact: 실행 증거(plan · diff · log · file · test_result · quality_report · orchestration_plan · snapshot).
  • QualityGate: build · tests · smoke · changed · known_risks · evidence refs 평가. passed / warning만 markDone 허용.

BLOCK FLOOR — 우회 불가 정책

Auto-approve가 켜져 있어도 Agent Profile의 blockedActions에 포함된 action type은 항상 차단된다. shouldAutoApprove 결정 함수의 첫 단계에서 검사하기 때문에 어떤 설정으로도 우회할 수 없다.

Auto-approve 7단계 결정 흐름

  1. blocked_action — profile blocks → 차단
  2. policy_blocked — service-layer policy 차단
  3. budget_blocked — profile budget 초과 → 차단 신규
  4. profile_auto_approve — profile 명시 허용
  5. policy_disallow_auto — manual-only policy
  6. worker_file_action — 좁은 worker file 자동화
  7. global_toggle — 전역 자동 승인 토글

05사용법 — 첫 작업 흐름

1. 첫 설정

  • 좌측 레일 → 설정 → Agents: 작업에 사용할 Agent Profile을 선택하거나 새로 만든다. 한국어 role 프롬프트, 모델, action 권한, Budget(선택)을 설정.
  • 설정 → Pipelines: 여러 step을 묶고 싶다면 파이프라인을 만든다. 각 step의 instruction · output contract · 허용 action 지정.
  • 설정 → MCP / Skills / Secrets: 외부 도구, skill 패키지, API key 등록.

2. 작업 시작

  • 좌측 패널에서 새 Thread 생성: target directory(작업할 폴더)를 선택. Renderer는 폴더에 직접 접근하지 않고 IPC를 통해 검증.
  • 대화 입력: 한국어로 자연스럽게 요청. 필요하면 Pipeline 드롭다운에서 미리 만들어둔 흐름을 선택.
  • 중앙 타임라인: TaskRun이 생기고 agent가 plan을 작성한다. Plan은 자연어 + 파싱 가능한 block으로 구성.

3. 승인하기

  • 우측 Plan > Approvals: 제안된 action들을 검토. 각 카드의 "결정 trace" 토글로 자동 승인 / 차단된 사유 확인.
  • 위험한 action: git_commit, shell 등은 BLOCK FLOOR에 묶어두면 자동 승인 토글로도 우회 불가.
  • 비용이 큰 model_use: Budget 한도를 넘으면 budget 단계에서 자동 승인 차단됨. 사용자가 수동으로 승인 가능.

4. 실행 · 증거 · 완료

  • 승인된 action은 Runner를 통해 실행되고 artifact(stdout / diff / file / test report)가 남는다.
  • 우측 QA 패널에서 QualityGate가 evidence를 평가한다. failed 시 RepairLoop이 자동으로 재시도(최대 2회).
  • passed / warning이면 Mark Done 가능. 결과를 다시 검토 후 마무리.

5. 진행 중 통제

  • Pause / Resume / Retry / Cancel: 우측 액션 영역에서 비종료 상태일 때만 노출.
  • Retry: blocked / quality_failed 상태에서 가장 최근 승인된 action을 idempotent runner 경로로 재실행.
  • Cancel: 비어있지 않은 사유와 함께 quality_report artifact 기록.

06최근 추가된 안전 기능

Phase 1~3에서 사용자 감독 정확도를 높이기 위해 새로 들어간 기능들.

Pre-Execution Budget Gate

Agent Profile의 Budget 섹션에서 호출당 · TaskRun 누적 · 일일 누적 USD 한도를 설정. evaluateBudget이 정책 단계의 한 step으로 동작하여 추정 비용이 초과되는 자동 승인을 차단.

perInvocationUsd perTaskRunUsd perDayUsd

Auto-Approve Decision Trace

모든 자동 승인 결정에 대해 7단계 중 어느 단계가 판단했는지 + 사유가 approval row에 저장된다. 각 approval 카드에서 "결정 trace" 토글로 확인.

approved decidedAt reason

Cancellation Cleanup Chain

cancelInvocation 호출 시 AgentInvocation의 child CLI process까지 SIGTERM → grace period → SIGKILL 순서로 종료. ShellRunner도 외부 AbortSignal을 수용.

AbortSignal SIGTERM → SIGKILL
Phase 3.5 진행 예정: 현재 Cancellation은 AgentInvocation 경로에서만 완결됐고, RunnerService.executeApproved → ShellRunner 경로에서는 signal 전파가 끊겨있다. TaskRun 자체를 사용자가 중단할 IPC entry(cancelExecution)도 추가 예정. 자세한 내용은 harness-supervision-hardening-plan.md §7-A 참고.

07새 기능을 추가하려면 — 9-레이어 IPC 패턴

새 IPC 도메인 추가 시 반드시 9개 레이어를 순서대로 수정한다. 누락 시 빌드/타입체크가 실패.

#레이어위치
1HarnessDesktopApi 인터페이스packages/core/src/api.ts
2필요한 타입packages/core/src/types/
3Repository / Service (필요 시)packages/storage
4해당 packages 서비스 — 비즈니스 로직packages/{runners,quality,...}
5IPC 핸들러apps/desktop/electron/ipc/{domain}-ipc.ts
6등록 함수 (필요 시){domain}-ipc-register.ts
7registerAllIpc에 추가apps/desktop/electron/ipc/index.ts
8contextBridge exposeapps/desktop/electron/preload.ts
9Renderer 타입 선언apps/desktop/src/types/window.d.ts

절대 위반 금지 6가지

  • packages/core는 @harness/storage를 import 하지 않는다. core는 순수 타입/인터페이스만.
  • 테스트 파일은 반드시 .test.mjs로 끝난다 (.test.ts/.test.tsx 금지).
  • Renderer에서 nodeIntegration 비활성화 유지 — window.harness.*만 호출 가능.
  • Express / localhost / WebSocket 서버 추가 금지 — UI ↔ Core 통신은 Electron IPC만.
  • JSON을 canonical state로 사용 금지 — SQLite WAL이 유일한 source of truth.
  • Approval 없이 side effect(파일 쓰기, shell, git commit 등) 실행 금지.

08FAQ · 트러블슈팅

npm run dev가 실행되지 않습니다.

대부분 native module 재빌드가 필요한 경우다. npm run rebuild:electron 후 다시 시도.

승인된 action이 실행되지 않습니다.

3가지를 순서대로 확인. (1) Agent Profile의 blockedActions에 해당 action type이 있는지. (2) Budget 한도를 초과했는지. (3) Approval row의 "결정 trace"를 펼쳐 어느 단계에서 멈췄는지 확인.

비용이 너무 많이 나옵니다.

설정 → Agents에서 사용하는 profile의 Budget 섹션에 perInvocationUsd, perTaskRunUsd, perDayUsd 한도를 설정. Learner의 추정 비용이 한도를 넘으면 자동 승인이 차단된다.

외부에서 데이터를 가져올 수 있나요?

HarnessAgentOS는 의도적으로 서버를 두지 않는다. 모든 상태는 로컬 SQLite WAL에 보관된다. 외부 동기화는 Git을 통해 수동으로 한다.

여러 사용자가 동시에 쓸 수 있나요?

아니오. 단일 사용자 데스크톱 워크벤치다. 멀티 유저는 의도적으로 지원하지 않는다.

QualityGate가 항상 failed로 나옵니다.

artifact가 부족하거나 known_risks가 등록되어 있을 가능성. 우측 QA 패널 → Evidence refs에서 어떤 evidence가 누락됐는지 확인. build · tests · smoke · changed 각각의 통과 여부 표시.

새 IPC를 추가하려면?

위 9-레이어 IPC 패턴을 정확히 따른다. packages/core/src/api.ts부터 시작해 9개 레이어를 모두 수정해야 빌드 통과.
