HarnessAgentOS · 동작 흐름 시각화

사용자가 메시지를 보낸 순간부터
완료까지의 모든 길

HarnessAgentOS는 사용자 감독형 개발 워크벤치입니다. 에이전트가 자율적으로 움직이는 게 아니라 — 사용자가 입력 → 승인 → 실행의 체인을 직접 통제합니다. 이 문서는 그 체인이 두 가지 경로(파이프라인 선택 vs 미선택)에서 어떻게 갈라지는지, 그리고 각 기능이 그 안에서 어떤 자리에서 어떤 일을 하는지를 그림으로 풀어냅니다.

레이어: Renderer → Preload → Main → Services 데이터: SQLite WAL (single source of truth) 통신: window.harness.* IPC
01 — ARCHITECTURE

먼저 큰 그림: 4개의 레이어, 8개의 패키지

UI는 window.harness.* 한 줄로만 백엔드를 만집니다. 모든 사이드이펙트(파일/Shell/CLI/DB)는 Main 프로세스 안의 서비스가 책임지고, Renderer는 SQL도 파일도 못 만집니다.

Renderer UI
IPC · Bridge
도메인 서비스
CLI · 외부 프로세스
저장소 / 외부
💡
핵심 규칙 · Renderer는 SQL/파일/process를 직접 만지지 않는다. window.harness.* 외의 채널은 없다. 그래서 모든 흐름은 항상 UI → IPC → Service → 저장소/CLI의 단방향 호출을 따른다.
02 — TWO FORKS

같은 입력, 두 가지 갈림길

사용자가 입력창에서 메시지를 보내는 순간, 코드는 단 한 가지를 본다: 이 메시지에 orchPipelineId가 있는가? 이 한 줄이 라우팅을 완전히 가른다. (WorkbenchShell.handleCreateTask 분기점)

A · 파이프라인 선택 후 질문

오케스트레이션이 응답 생성을 통째로 소유

드롭다운에서 파이프라인을 골라 보내면 orchestration.draftPlan이 호출되고 파이프라인의 step 순서대로 워커가 실행된다. 사용자의 선택 자체가 승인으로 간주되어 플랜이 자동 승인·실행된다.

  1. conversation.createTask → TaskRun 생성 + pipeline-auto 마킹
  2. orchestration.draftPlan({ pipelineId, mode }) 호출
  3. OrchestrationPlanner.synthesizeFromPipeline()이 step별 instruction 합성
  4. orchestration_plan approval 생성 → 즉시 자동 승인 ("per-message pipeline pick")
  5. runApproved → 각 step의 persona+instruction으로 CLI 호출 → Artifact 누적
B · 파이프라인 미선택 후 질문

모드(Template / Agent)에 따라 한 번 더 갈라짐

드롭다운이 비어 있으면 일반 채팅 경로. 여기서 모드가 template이면 사전 정의 계획만 표시, agent면 실제 CLI가 호출되어 스트리밍 응답이 나온다.

  1. conversation.createTask → TaskRun 생성
  2. Agent 모드: capability.proposeCandidates + learner.proposeRecommendation 먼저 호출
  3. advisory approval이 0개이고 Agent 모드라면 → agent.generatePlan 자동 트리거
  4. CLI 스트리밍 → ApprovalRequest들 생성 → Plan 탭에서 사용자 수동 결정
  5. Template 모드: CLI 호출 없음. 정적 plan만 표시 → 사용자 수동 승인 후 runner 실행
03 — SCENARIO A

시나리오 A · 파이프라인을 골라서 보냈을 때

예: 스레드 헤더에 Pipeline: code-review 배지가 있고, 입력창 드롭다운도 같은 값. 이 메시지는 일반 채팅 트랙으로 가지 않고 오케스트레이션 라인으로 들어간다.

🔑
이 경로의 본질 · 파이프라인을 고른다는 행위 자체가 "이 단계들을 그대로 실행해 달라"는 사전 동의로 처리됩니다. 그래서 매번 Approval 다이얼로그가 뜨지 않습니다. 단, AgentProfile의 blockedActions는 파이프라인 픽으로도 우회되지 않습니다 — 명시적 금지가 항상 최우선입니다.
04 — SCENARIO B

시나리오 B · 파이프라인을 안 골랐을 때

이때는 일반 채팅 경로. 모드 버튼(Template / Agent)이 다음 분기를 결정한다. 코드는 두 모드를 분명히 다르게 다룬다.

Template 모드

"CLI 없이도 일단 한 번 굴려보고 싶을 때"

Claude/Codex가 PATH에 없거나, 단순 문서 수정처럼 굳이 모델을 안 써도 되는 작업. 사전 정의된 ActionPlan을 그대로 보여주고 사용자가 검토해서 승인하면 runner가 실행한다. 자동 승인 없음, CLI 호출 없음.

Agent 모드

"실제 CLI에게 시킨다"

상태바에 Claude ● 혹은 Codex ●가 초록일 때만 활성화. capability/learner 추천이 먼저 큐잉되고, advisory가 0이면 곧장 agent.generatePlan이 트리거되어 스트리밍 응답이 우측 패널 Agent 탭에 흐른다.

05 — FEATURE FLOWS

각 기능이 동작할 때 안에서 일어나는 일

위 두 시나리오 안에 자리 잡은 작은 부품들. 각 부품이 호출되는 순간 어떤 패키지가 일하고 어떤 저장소가 갱신되는지 짧게 짚는다.

🧵

Thread 생성

프로젝트 단위의 작업 묶음을 만든다. 대상 폴더와 기본 파이프라인을 함께 묶을 수 있다.

UI: ThreadSidebar IPC: state.createThread DB: threads (pipeline_id)
사용자 + 새 작업 → 폼 입력
window.harness.state.createThread()
ThreadRepository.insert (pipeline_id 포함)
setSelectedThreadId(created.id)
Workbench 빈 상태로 전환
⚙️

TaskRun 생성

메시지 하나 = TaskRun 하나. 응답·승인·아티팩트가 이 record에 매달려 자라난다.

UI: ConversationInput IPC: conversation.createTask DB: task_runs · steps
Enter 또는 [전송]
handleCreateTask({ userRequest, mode, orchPipelineId? })
TaskRun INSERT (status: drafting)
파이프라인 있으면 pipelineAutoTaskRunIdsRef 마킹
분기 1: orchestration / 분기 2: agent / 분기 3: template
🛡

Approval 결정

사이드이펙트 직전의 마지막 관문. 승인 없이는 runner가 실행되지 않는다.

IPC: conversation.approve / .reject DB: approvals (status) Runner: executeApproved
pending approval → 4가지 결정
승인 → runner.executeApproved
이번 실행 전체 승인 → 같은 actionType 일괄 승인 큐
거부 → 이유 기록 · checkpoint 생성
재지시 → 새 instruction으로 plan 재생성
🧩

Capability 제안

prompt를 보고 어떤 스킬을 추가로 컨텍스트에 넣을지 후보를 만들어 사용자에게 동의를 받는다.

IPC: capability.proposeCandidates Pkg: skillify-adapter Approval: capability_use
Agent 모드 createTask 직후 호출
CapabilityRegistry.match(prompt)
capability_use approval 큐잉
승인 시 다음 agent 호출 prompt에 합쳐짐
📚

Learner 추천

과거 TaskRun의 LearningTrace에서 모델/접근법을 골라 다음 호출에 반영하도록 제안한다.

IPC: learner.proposeRecommendation Pkg: learner (LearnerAdvisor) Approval: model_use
capability 제안 직후 같은 자리에서 호출
LearnerAdvisor.recommend(trace history)
model_use approval 큐잉
advisoryApprovalCount > 0 이면 자동 generatePlan 보류
🎼

Orchestration (Worker 실행)

파이프라인의 step들을 순서대로 굴린다. step마다 persona+instruction을 CLI에 주입한다.

IPC: orchestration.draftPlan / runApproved Pkg: orchestration (Planner + WorkerRunner) Approval: orchestration_plan
draftPlan → synthesizeFromPipeline → WorkerStep[]
orchestration_plan approval 생성
runApproved → WorkerRunner.run()
step 순회 → AgentPlanningService → CLI
artifacts/checkpoints 누적 → done
🛠

Runner 실행 (file/shell/git/test)

approval이 떨어진 ActionPlanItem을 실제 시스템에 적용한다. 모든 사이드이펙트의 종착지.

IPC: runner.executeApproved Pkg: runners (RunnerService) Artifact: file / shell-log / git-diff / test-report
approval.actionType 확인
file_write / shell / git_commit / test_run 분기
subprocess 또는 fs 호출 → 결과 캡처
Artifact INSERT · Step status 갱신
onTaskRunChanged 이벤트 push → UI 갱신
✅

Quality Gate

실행 산출물(테스트 결과, diff 등)을 evidence로 모아 passed / warning / failed 판정.

IPC: quality.evaluate Pkg: quality (QualityEvaluator) Action: markDone
Artifact 수집 (test logs, diff 등)
QualityEvaluator.evaluate(evidence)
quality_gate row 기록 (passed/warning/failed)
passed 또는 warning일 때만 markDone 허용
📡

실시간 스트리밍 (push 이벤트)

polling 대신 main → renderer push. agent 토큰 스트림과 TaskRun 변경을 즉시 반영한다.

UI: WorkbenchShell useEffect 구독 IPC: events.onAgentStreamEvent · onTaskRunChanged Refetch: getTaskRunDetail / getThreadDetail
events 채널에서 push 수신
progress 이벤트 → pushAgentProgress(taskRunId, event)
started/result/failed → refreshProviders
선택된 TaskRun이면 detail re-fetch
🎛

⚙ Agents 패널 (Orchestration 설정)

Worker 프로필과 실행 모드(Single / Planner+Worker / Multi)를 정의한다. 새 메시지부터 적용.

UI: OrchestrationPanel IPC: settings.update DB: settings (orchestration JSON)
사이드바 ⚙ Agents 클릭
Worker 추가 · 역할/Provider/Model 지정
저장 → settings JSON normalize 후 UPSERT
다음 generatePlan부터 새 설정 적용
🤖

자동 승인 (4가지 트리거)

사용자 부담을 줄이는 사전 동의 시스템. 단, AgentProfile의 BLOCK LIST는 항상 절대 우선.

trigger: global autoApprove trigger: profile per-action allow trigger: worker-file auto-execute trigger: pipeline-pick consent
useEffect가 pending approval 감시
blockedActions 포함되면 절대 자동승인 안 함
4개 트리거 중 하나라도 맞으면 approve()
actionType별 분기: orchestration_plan vs runner vs advisory
📑

Right Panel — TaskRun 7개 탭

선택한 TaskRun을 들여다보는 단일 페인. 7개 탭이 같은 detail 객체에서 각자 보기를 만든다.

Plan · Agent · Timeline · Artifacts Quality · Capabilities · Orchestration
conversation.getTaskRunDetail(id)
detail.taskRun / approvals / checkpoints / artifacts / qualityGate / capabilities
탭마다 같은 detail을 다르게 슬라이스
onTaskRunChanged push → 자동 re-fetch
