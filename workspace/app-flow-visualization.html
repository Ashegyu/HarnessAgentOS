HarnessAgentOS · 동작 흐름 시각화

사용자가 메시지를 보낸 순간부터
완료까지의 모든 길

HarnessAgentOS는 사용자 감독형 개발 워크벤치입니다. 에이전트가 자율적으로 움직이는 게 아니라 — 사용자가 입력 → 승인 → 실행의 체인을 직접 통제합니다. 이 문서는 그 체인이 두 가지 경로(파이프라인 선택 vs 미선택)에서 어떻게 갈라지는지, 그리고 각 기능이 그 안에서 어떤 자리에서 어떤 일을 하는지를 그림으로 풀어냅니다.

레이어: Renderer → Preload → Main → Services 데이터: SQLite WAL (single source of truth) 통신: window.harness.* IPC
01 — ARCHITECTURE

먼저 큰 그림: 4개의 레이어, 8개의 패키지

UI는 window.harness.* 한 줄로만 백엔드를 만집니다. 모든 사이드이펙트(파일/Shell/CLI/DB)는 Main 프로세스 안의 서비스가 책임지고, Renderer는 SQL도 파일도 못 만집니다.

02 — DATA MODEL · STATE MACHINE

도메인을 받치는 9개의 테이블과 한 장의 상태 다이어그램

모든 흐름은 결국 SQLite WAL의 row 변경으로 끝난다. 도메인 객체의 모양과 TaskRun.status가 거치는 9가지 상태를 머리에 박아두면, 어떤 화면을 보고 있든 "지금 DB에 무엇이 기록됐고 다음 어떤 row가 추가될지"를 예측할 수 있다.

2-1 · Entity 관계도

컬럼 명명 규약

JSON은 _json 접미사

known_risks_json, trigger_terms_json, proposed_action_json, policy_evaluation_json, evidence_artifact_ids_json … 저장은 string이지만 의미는 구조화 JSON. 직접 SQL로 만지지 말고 Repository 경유로만 접근.

Timestamp 규약

모든 시간은 ISO string

created_at, updated_at, started_at, finished_at, decided_at, archived_at 전부 ISO-8601. Unix epoch나 number 금지.

SQLite 설정

WAL · FK 강제 · busy 5s

PRAGMA journal_mode=WAL, foreign_keys=ON, busy_timeout=5000. migration은 SCHEMA_VERSION으로 추적, IF NOT EXISTS로 idempotent.

2-2 · TaskRun 상태 머신 (9개 상태 · 실제 전이만)

정상 진행 (approve · markDone)
품질 게이트 분기
실패 · 거절
특수 경로 (취소 · answer-only)

2-3 · 보조 상태 enum

Enum 가능한 값 의미
ApprovalStatus pending approved rejected always_approved_for_run executed 승인 결정 + 실행 추적. always_approved_for_run은 같은 actionType 일괄 승인, executed는 runner 후의 종착.
AgentInvocationStatus queued running succeeded failed cancelled CLI 호출 1건의 lifecycle. queueDepth가 RuntimeStatusBar에 표시되어 대기열 길이를 알 수 있다.
QualityGateStatus passed warning failed not_run passed·warning만 markDone 허용. failed는 repair loop, not_run은 평가 전 초기값.
StepStatus / WorkerStepStatus pending running succeeded failed skipped step과 worker step 공통. 파이프라인 step 단위 진행 표시에 사용.
ArtifactKind plan diff log test_result quality_report orchestration_plan file snapshot 모든 산출물은 8개 kind 중 하나. Right Panel의 Artifacts 탭이 kind별로 슬라이스한다.
ApprovalActionType capability_use model_use file_write shell dependency_install git_commit network skill_script orchestration_plan 2종(advisory)은 consent-only — runner 호출 없이 다음 prompt에만 반영. 6종은 runner 측 사이드이펙트. 1종은 worker pipeline 실행 트리거.
🗺
상태가 헷갈릴 때의 단서 · blocked는 시스템이 자체적으로 멈춘 것(예외/실패), paused는 사용자가 명시적으로 멈춘 것. quality_failed는 실행이 끝났지만 게이트가 막은 것, ready_for_review는 게이트가 통과했거나 부수효과가 없어 markDone만 남은 것. 의미가 비슷해 보이지만 회복 경로가 다 다르다.
03 — TWO FORKS

같은 입력, 두 가지 갈림길

사용자가 입력창에서 메시지를 보내는 순간, 코드는 단 한 가지를 본다: 이 메시지에 orchPipelineId가 있는가? 이 한 줄이 라우팅을 완전히 가른다. (WorkbenchShell.handleCreateTask 분기점)

A · 파이프라인 선택 후 질문

오케스트레이션이 응답 생성을 통째로 소유

드롭다운에서 파이프라인을 골라 보내면 orchestration.draftPlan이 호출되고 파이프라인의 step 순서대로 워커가 실행된다. 사용자의 선택 자체가 승인으로 간주되어 플랜이 자동 승인·실행된다.

  1. conversation.createTask → TaskRun 생성 + pipeline-auto 마킹
  2. orchestration.draftPlan({ pipelineId, mode }) 호출
  3. OrchestrationPlanner.synthesizeFromPipeline()이 step별 instruction 합성
  4. orchestration_plan approval 생성 → 즉시 자동 승인 ("per-message pipeline pick")
  5. runApproved → 각 step의 persona+instruction으로 CLI 호출 → Artifact 누적
B · 파이프라인 미선택 후 질문

모드(Template / Agent)에 따라 한 번 더 갈라짐

드롭다운이 비어 있으면 일반 채팅 경로. 여기서 모드가 template이면 사전 정의 계획만 표시, agent면 실제 CLI가 호출되어 스트리밍 응답이 나온다.

  1. conversation.createTask → TaskRun 생성
  2. Agent 모드: capability.proposeCandidates + learner.proposeRecommendation 먼저 호출
  3. advisory approval이 0개이고 Agent 모드라면 → agent.generatePlan 자동 트리거
  4. CLI 스트리밍 → ApprovalRequest들 생성 → Plan 탭에서 사용자 수동 결정
  5. Template 모드: CLI 호출 없음. 정적 plan만 표시 → 사용자 수동 승인 후 runner 실행
04 — SCENARIO A

시나리오 A · 파이프라인을 골라서 보냈을 때

예: 스레드 헤더에 Pipeline: code-review 배지가 있고, 입력창 드롭다운도 같은 값. 이 메시지는 일반 채팅 트랙으로 가지 않고 오케스트레이션 라인으로 들어간다.

🔑
이 경로의 본질 · 파이프라인을 고른다는 행위 자체가 "이 단계들을 그대로 실행해 달라"는 사전 동의로 처리됩니다. 그래서 매번 Approval 다이얼로그가 뜨지 않습니다. 단, AgentProfile의 blockedActions는 파이프라인 픽으로도 우회되지 않습니다 — 명시적 금지가 항상 최우선입니다.
05 — SCENARIO B

시나리오 B · 파이프라인을 안 골랐을 때

이때는 일반 채팅 경로. 모드 버튼(Template / Agent)이 다음 분기를 결정한다. 코드는 두 모드를 분명히 다르게 다룬다.

Template 모드

"CLI 없이도 일단 한 번 굴려보고 싶을 때"

Claude/Codex가 PATH에 없거나, 단순 문서 수정처럼 굳이 모델을 안 써도 되는 작업. 사전 정의된 ActionPlan을 그대로 보여주고 사용자가 검토해서 승인하면 runner가 실행한다. 자동 승인 없음, CLI 호출 없음.

Agent 모드

"실제 CLI에게 시킨다"

상태바에 Claude ● 혹은 Codex ●가 초록일 때만 활성화. capability/learner 추천이 먼저 큐잉되고, advisory가 0이면 곧장 agent.generatePlan이 트리거되어 스트리밍 응답이 우측 패널 Agent 탭에 흐른다.

07 — GUARDRAILS · RECOVERY

승인은 누가 한 번에 풀어주고, 실패는 어떻게 되돌리는가

06장의 각 기능이 정상 케이스라면 이 장은 "예외와 우회". 자동승인이 어떤 트리거에서 어떤 actionType에 적용되는지, 그리고 흐름이 어디서 끊겼을 때 코드가 어떻게 회복 경로를 제시하는지를 한 자리에 모았다.

7-1 · 자동승인 4×9 매트릭스

트리거 ① · 글로벌 토글

모든 pending approval에 적용

HarnessSettings.approval.autoApprove가 true면 useEffect가 pending approval을 감시하다가 shouldAutoApprove() 통과 시 conversation.approve() 호출. 메시지는 auto-approved (settings.approval.autoApprove)로 기록.

트리거 ② · 프로필 권한

per-action ALLOW list

활성 AgentProfile.permissions.autoApproveActions에 포함된 actionType만 자동승인. 글로벌 토글이 꺼져 있어도 적용. blockedActions가 항상 우선.

트리거 ③ · 워커 파일 자동실행

좁은 범위, 안전한 차단

approval.autoExecuteWorkerFileActions가 true이고 해당 approval이 isWorkerFileActionApproval() 통과 시에만 자동승인. WorkerStep이 생성한 file_write approval에만 한정 — 일반 채팅의 file_write는 제외.

트리거 ④ · 파이프라인 픽 동의

가장 광범위, 가장 명시적

pipelineAutoTaskRunIdsRef에 들어 있는 TaskRun에서 나오는 모든 approval은 block list 제외 모두 자동승인. autoInFlightRef.add()로 pre-claim해 글로벌 토글과의 race를 막는다 ("approval is executed" 에러 방지).
