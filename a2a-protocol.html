배경

왜 A2A가 필요한가

엔터프라이즈에서 멀티 에이전트 시스템을 구축할 때 가장 큰 문제는 파편화였다. 서로 다른 벤더의 에이전트들은 공통 표준 없이 각자의 내부 메시지 포맷을 사용했고, 새로운 에이전트 쌍마다 별도의 커스텀 커넥터가 필요했다.

2024
MCP 등장 (Anthropic)
에이전트 ↔ 툴/데이터 연결 표준화. 하지만 에이전트 간 통신 표준은 부재
2025.04.09
A2A 발표 — Google Cloud Next
50개 이상의 파트너사와 함께 오픈 스펙 공개. HTTP, SSE, JSON-RPC 2.0 기반
2025.06.23

🎯
핵심 문제 해결
벤더 A의 Salesforce 에이전트와 벤더 B의 ServiceNow 에이전트가 공통 표준 없이 직접 통신하려면 커스텀 브릿지 코드가 필요했다. A2A는 이 통합 비용을 표준 HTTP 엔드포인트 하나로 줄인다.
🔗
MCP와의 관계
A2A는 MCP를 대체하지 않는다.
MCP = 에이전트 ↔ 툴/데이터 (수직)
A2A = 에이전트 ↔ 에이전트 (수평)

단일 에이전트는 MCP로 도구를 호출하고, 에이전트 간 태스크 위임에는 A2A를 사용한다.

5가지 핵심 원칙

Google이 파트너들과 함께 A2A를 설계할 때 지킨 원칙들

01
🤖
에이전트 본연의 능력 수용
에이전트를 단순 도구가 아닌 자율 행위자로 취급. 멀티모달 교환, 메모리, 멀티턴 대화를 지원.
02
📡
기존 표준 위에 구축
HTTP, SSE, JSON-RPC 2.0 등 기업 인프라에서 이미 사용 중인 표준 활용. 새로운 transport 발명 없음.
03
🔒
보안 기본 내장
OAuth 2.0, PKCE, API Key 기본 지원. 내부 로직·메모리를 노출하지 않고 에이전트 간 협업 가능.
04
🔄
장기 실행 태스크 지원
수 분~수 일이 걸리는 태스크도 지원. SSE 스트리밍으로 중간 진행 상황 전달. 웹훅 기반 푸시 알림 지원.
05
🌐
모달리티 무관
텍스트, 파일, 이미지, 오디오, 비디오, 구조화 데이터 어떤 형식도 지원. 에이전트 간 UI 협상으로 최적 포맷 선택.

🪪
Agent Card
에이전트가 /.well-known/agent.json에 게시하는 JSON 메타데이터. 이름, 설명, 버전, 엔드포인트, 지원 모달리티, 인증 방식을 담고 있다. AI 세계의 "명함".
agent card 예시 { "name": "HR Onboarding Agent", "version": "1.2.0", "url": "https://hr.acme.com/a2a", "skills": [{ "id": "create_ticket", "description": "HR 티켓 생성" }], "defaultInputModes": ["text", "data"] }
📋
Task
A2A의 작업 단위. 고유 ID를 가지며 정의된 라이프사이클 상태를 거친다. 즉시 완료되거나 장기 실행 작업일 수도 있으며, 완료 시 Artifacts(결과물)을 생성한다.
task object { "id": "d8c6243f-5f7a-4f6f", "contextId": "c295ea44-7543", "status": { "state": "TASK_STATE_WORKING", "timestamp": "2025-04-17T17:45:00Z" }, "artifacts": [] }
💬
Message
클라이언트 ↔ 원격 에이전트 간 하나의 통신 턴. "user" 또는 "agent" 역할을 가지며 하나 이상의 Part를 포함한다.
🧩
Part
메시지나 Artifact 내 콘텐츠 최소 단위. TextPart, FilePart, DataPart 세 종류가 있으며 멀티모달 콘텐츠를 구성할 수 있다.
📦
Artifact
태스크 결과로 생성되는 출력물. 문서, 이미지, 구조화 데이터 등 어떤 형식도 가능하며 여러 Part로 구성된다.

태스크 라이프사이클

태스크는 제출에서 완료까지 명확한 상태를 거친다. 장기 실행 태스크는 SSE 스트리밍 또는 웹훅으로 진행 상황을 전달한다.

* input-required: 원격 에이전트가 추가 정보를 요청. 클라이언트는 tasks/get으로 폴링하거나 SSE로 실시간 업데이트를 받는다.

📡
SSE 스트리밍
장기 실행 태스크에서 실시간으로 상태 변경·아티팩트 청크를 전달. 단일 HTTP 연결 유지로 polling 오버헤드 없음. tasks/sendSubscribe 메서드 사용.
🔔
Push Notifications (Webhook)
연결이 끊어진 시나리오에서 서버가 클라이언트 제공 URL로 HTTP POST 전송. 장기 작업(수 시간 ~ 수 일)에 적합. 클라이언트는 작업을 시작하고 나중에 결과를 수신.

A2A vs MCP

두 프로토콜은 경쟁이 아닌 상호 보완 관계다. 각 레이어에서 서로 다른 문제를 해결한다.

A2A LAYER
🤖 ↔ 🤖
에이전트 ↔ 에이전트
태스크 위임 · 발견 · 협업 (수평)
MCP LAYER
🤖 ↔ 🔧
에이전트 ↔ 툴/데이터
API · DB · 파일시스템 연결 (수직)

흔한 패턴: 플래너 에이전트 → A2A로 전문 에이전트에 위임 → 각 에이전트는 MCP로 필요한 도구 호출

활용 사례

A2A 적용 시나리오

다양한 엔터프라이즈 도메인에서의 실제 활용 패턴

01 / HR
채용 자동화 파이프라인
채용 에이전트 → 이력서 심사 에이전트 → 면접 일정 에이전트 → 온보딩 에이전트. 각 에이전트는 독립 벤더 시스템에서 Agent Card로 서로를 발견해 협력.
02 / SUPPLY CHAIN
공급망 최적화
재고 에이전트가 부족 감지 → A2A로 공급업체 에이전트에 발주 → 배송 에이전트 업데이트. MCP로 각 에이전트가 개별 DB 접근, A2A로 에이전트 간 조율.
03 / IT OPS
멀티 도메인 IT 운영
헬프데스크 에이전트 → 인시던트 에이전트 → 네트워크 모니터링 에이전트. 각 도메인 에이전트가 전문화된 역할로 A2A 협력.
04 / FINANCE
보험 언더라이팅
언더라이팅 에이전트가 수동 검토 단계에서 A2A로 인간 인터페이스 에이전트에 위임. 백그라운드 처리 중 담당자 검토 완료 후 재개.
05 / SALES
리드 관리 자동화
마케팅 에이전트가 리드 평가 후 A2A로 영업 에이전트에 전달. CRM 데이터 참조해 맞춤 영업 가이드 생성 후 Slack으로 담당자에게 전달.
06 / RESEARCH
멀티 에이전트 리서치
오케스트레이터 에이전트 → 웹 검색 에이전트 + 문서 분석 에이전트 + 요약 에이전트 병렬 처리 후 취합해 최종 리포트 생성.

핵심 통찰

✅ A2A 선택 시점
  • →서로 다른 벤더의 에이전트가 협력해야 할 때
  • →수 분~수 일의 장기 실행 비동기 워크플로우
  • →에이전트 내부 구현을 노출하지 않고 태스크 위임
  • →규제 환경에서 감사 가능한 에이전트 간 통신
🔌 MCP 선택 시점
  • →단일 에이전트가 DB, API, 파일에 접근할 때
  • →IDE 플러그인, 챗봇 등 호스트 애플리케이션
  • →의료·금융 등 강력한 거버넌스가 필요한 환경
핵심 통찰 4가지
A2A는 "에이전트 인터넷"의 HTTP다
HTTP가 웹 서버 간 통신을 표준화한 것처럼, A2A는 AI 에이전트 간 통신의 공통어가 되려 한다.
MCP와 A2A는 레이어가 다르다
MCP = 수직(에이전트↔툴), A2A = 수평(에이전트↔에이전트). 대부분의 엔터프라이즈 아키텍처에서 두 프로토콜은 함께 사용된다.
Linux Foundation이 중립성을 보장
Google이 시작했지만 Linux Foundation에 기여됨으로써 특정 벤더 종속 없는 오픈 거버넌스를 확보했다.
보안은 여전히 구현체의 책임
A2A가 OAuth 2.0 등 인증 프레임워크를 내장하지만, OWASP LLM 최대 위협인 간접 프롬프트 인젝션은 프로토콜만으로 해결 불가.

실전 구현 — C# / .NET

.NET SDK로 A2A 구현하기

dotnet add package A2A  +  dotnet add package A2A.AspNetCore 두 패키지로 A2A 서버와 클라이언트를 모두 구현할 수 있다.

🖥️
A2A Server (Remote Agent)
ASP.NET Core + MapA2A()
Program.cs // 1. 패키지 설치 // dotnet add package A2A // dotnet add package A2A.AspNetCore using A2A; using A2A.AspNetCore; var builder = WebApplication.CreateBuilder(args); var app = builder.Build(); // TaskManager 생성 (태스크 라이프사이클 관리) var taskManager = new TaskManager(); var agent = new EchoAgent(); agent.Attach(taskManager); // A2A 엔드포인트 등록 (/echo) app.MapA2A(taskManager, "/echo"); app.Run(); public class EchoAgent { public void Attach(ITaskManager tm) { tm.OnMessageReceived = ProcessMessageAsync; tm.OnAgentCardQuery = GetAgentCardAsync; } private Task<Message> ProcessMessageAsync( MessageSendParams p, CancellationToken ct) { var text = p.Message.Parts .OfType<TextPart>().First().Text; return Task.FromResult(new Message { Role = MessageRole.Agent, MessageId = Guid.NewGuid().ToString(), Parts = [new TextPart { Text = $"Echo: {text}" }] }); } private Task<AgentCard> GetAgentCardAsync( string agentUrl, CancellationToken ct) { return Task.FromResult(new AgentCard { Name = "Echo Agent", Description = "메시지를 그대로 반환", Url = agentUrl, Version = "1.0.0", Capabilities = new AgentCapabilities { Streaming = true } }); } }
💻
A2A Client (Client Agent)
A2ACardResolver + A2AClient

.NET SDK 핵심 클래스

⚙️
TaskManager
태스크의 생성·업데이트·취소·이벤트 스트리밍을 관리. 메시지 기반과 태스크 기반 두 가지 패턴 모두 지원.
🔍
A2ACardResolver
원격 에이전트의 Agent Card를 /.well-known/agent.json에서 자동 로드. 에이전트 발견의 진입점.
📡
A2AClient
스트리밍/논스트리밍 통신, 태스크 관리, 푸시 알림 수신 지원. SSE 기반 실시간 업데이트 처리.
💾
ITaskStore
태스크 영속성 인터페이스. 개발/테스트용 InMemoryTaskStore는 프로덕션 비권장 → 직접 구현 필요.
🌐
MapA2A() / MapHttpA2A()
ASP.NET Core 라우팅에 A2A 엔드포인트를 한 줄로 등록. JSON-RPC 및 HTTP REST 모두 자동 처리.
🤖
Semantic Kernel 통합
Travel Planner 샘플 포함. SK의 플러그인 체계를 A2A 에이전트로 노출 가능. samples/SemanticKernelAgent/
🔐
.NET SDK 보안 체크리스트 (공식 docs/security.md 기반)
책임 항목 처리 주체 권장 조치
인증 & 인가 앱 책임 SDK는 인증 미강제 → HTTP 미들웨어로 직접 구현
HTTPS / TLS 앱 책임 프로덕션 필수, SDK는 transport 보안 미강제
Rate Limiting 앱 책임 Kestrel / 리버스 프록시에서 설정
Webhook URL (SSRF) 앱 책임 저장 전 URL 유효성 검증, private IP 차단
태스크 스토리지 앱 책임 InMemoryTaskStore는 개발 전용 → ITaskStore 직접 구현
외부 에이전트 입력 앱 책임 AgentCard 필드 포함 모든 외부 에이전트 데이터를 untrusted로 처리, Prompt Injection 방어
