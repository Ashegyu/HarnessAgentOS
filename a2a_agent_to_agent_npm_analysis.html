A2A(Agent-to-Agent) 프로토콜 조사·분석 및 NPM 프로그램 적용 방안

Google이 공개하고 Linux Foundation 산하로 이관된 Agent2Agent(A2A) 프로토콜을 공식 문서, 공식 GitHub 저장소, Linux Foundation/Google/Microsoft/AWS 문서 중심으로 조사했다. 특히 NPM/TypeScript 기반 프로그램에 적용할 때 필요한 설계, 구현, 보안, 테스트, 마이그레이션 전략을 정리한다.

1. 핵심 결론

A2A = Agent ↔ Agent

에이전트를 단순 함수/툴로 호출하는 것이 아니라, 독립적이고 불투명한 원격 에이전트가 서로 발견, 메시지 교환, 작업 위임, 상태 추적, 산출물 교환을 하도록 만드는 애플리케이션 계층 프로토콜이다.

MCP와 보완 관계

MCP는 에이전트가 도구·API·데이터에 접근하는 계층이고, A2A는 에이전트끼리 협업하는 계층이다. 실전 시스템은 “에이전트 내부는 MCP, 에이전트 간 연결은 A2A” 조합이 자연스럽다.

NPM은 가능

공식 JavaScript SDK가 존재하며 npm install @a2a-js/sdk로 설치한다. 단, 기본 stable 문서는 A2A v0.3 기준이고, v1.0 지원은 @next alpha 라인으로 안내된다.

중요한 적용 판단: 지금 NPM 프로그램에 바로 적용한다면, 프로덕션 코어 로직을 A2A SDK에 직접 결합하지 말고 Adapter 계층을 둔다. 이유는 A2A v1.0 스펙은 production-ready로 발표되었지만, JavaScript stable SDK 쪽은 v0.3 호환 문서가 중심이고 v1.0은 alpha 라인으로 분리되어 있기 때문이다.
판단 항목결론프로그램 적용 의미
성숙도표준은 v1.0 production-ready로 발표. JS stable SDK는 v0.3 기반 안내.POC는 stable SDK, v1.0은 별도 브랜치/어댑터로 검증.
상호운용성JSON-RPC, HTTP+JSON/REST, gRPC 등 다중 바인딩 지향.초기에는 HTTP+JSON/REST 또는 JSON-RPC만 채택하고 gRPC는 Node 서버 전용 최적화 옵션으로 유지.
에이전트 발견/.well-known/agent-card.json 기반 공개 발견 또는 사설 Registry 방식.NPM 앱에 Agent Registry 모듈을 두고 캐싱/검증/권한을 담당.
작업 모델단발 응답은 Message, 장기 실행은 Task + status + artifact.UI/CLI는 task 상태 머신을 표시해야 하며, streaming/polling/webhook을 모두 고려.
보안HTTPS, OAuth/OIDC/API Key/mTLS 등 표준 웹 보안 체계에 위임.Agent Card에 비밀값 저장 금지. 인증 토큰은 HTTP header/out-of-band로 처리.

4.2 작업 상태 머신

상태의미클라이언트 처리
submitted서버가 작업을 접수.taskId/contextId 저장. UI에 대기 상태 표시.
working에이전트가 작업 처리 중.SSE 구독 또는 polling. 진행 메시지와 artifact update 표시.
input-required추가 사용자 입력이 필요.사용자에게 질문 표시. 동일 contextId/taskId로 후속 message 전송.
auth-required권한/인증이 추가로 필요.OAuth/OIDC 등 out-of-band 인증 플로우 실행. credential을 payload에 직접 넣지 않도록 설계.
completed성공적으로 완료.artifact 저장/표시. 완료 이벤트 기록.
failed오류로 실패.재시도 가능성 판단. error detail, retry-after, partial artifact 확인.
canceled취소됨.취소 요청자와 시각 기록. 중복 취소는 idempotent하게 처리.
rejected에이전트가 작업 수행을 거부.대체 에이전트 검색 또는 사용자에게 실패 사유 표시.

책임구현 내용주의점

5.6 A2A Server Adapter 책임

내 NPM 프로그램이 자체 에이전트를 외부에 제공해야 한다면 A2A server 역할도 필요하다. 이때 핵심은 “내부 에이전트 로직”과 “A2A transport”를 분리하는 것이다.

// 개념 예시: 실제 SDK 버전에 맞춰 import/API는 조정 필요
export interface InternalAgent {
  id: string;
  describe(): AgentProfile;
  run(input: AgentMessage, ctx: RunContext): AsyncGenerator<AgentEvent>;
  cancel?(taskId: string): Promise<void>;
}

export class A2AServerAdapter {
  constructor(private readonly agent: InternalAgent) {}

  // 1) Agent Card 제공
  getAgentCard() {
    const profile = this.agent.describe();
    return toA2AAgentCard(profile);
  }

  // 2) A2A request를 내부 agent event stream으로 변환
  async execute(a2aRequest: unknown, eventBus: EventBus) {
    const input = fromA2AMessage(a2aRequest);
    for await (const event of this.agent.run(input, buildRunContext(a2aRequest))) {
      eventBus.publish(toA2AEvent(event));
    }
    eventBus.finished();
  }
}

7. 보안·운영 설계

필수 보안 원칙

  • 프로덕션 A2A 통신은 HTTPS를 기본으로 한다.
  • 인증 정보는 JSON-RPC/메시지 payload에 넣지 않고 HTTP header 또는 out-of-band 흐름으로 처리한다.
  • Agent Card에는 static secret을 저장하지 않는다.
  • Agent Card가 내부 URL, 민감 skill, 권한 범위를 포함하면 인증된 endpoint로 제공한다.
  • Task 조회·취소·구독·push 설정은 모두 caller 권한으로 scope 제한한다.

Webhook/Push Notification 방어

  • 서버는 client가 제공한 webhook URL을 무조건 신뢰하지 않는다. SSRF 방지를 위해 allowlist, ownership verification, egress 제한을 둔다.
  • Webhook receiver는 서명/JWT/API key/mTLS 등으로 발신자 검증을 한다.
  • timestamp, nonce, jti를 사용해 replay attack을 방지한다.
  • long-running task는 polling, streaming, webhook 중 하나 이상 fallback 경로를 둔다.

운영 관측성

로그/메트릭필드목적
요청 추적contextId, taskId, messageId, agentName멀티 에이전트 호출 체인 추적.
라우팅 결과후보 agent, score, 제외 사유, 선택 사유잘못된 agent 선택 디버깅.

8. 적용 체크리스트

POC 전 체크

  • □ A2A로 연결할 “에이전트”와 MCP/도구로 충분한 “툴”을 구분했는가?
  • □ 각 agent의 skill, inputModes, outputModes를 명확히 정의했는가?
  • □ Agent Card에 민감 정보가 포함되는지 검토했는가?
  • □ stable SDK(v0.3)와 v1.0 alpha 차이를 adapter로 격리했는가?
  • □ message/task/artifact/contextId를 내부 도메인 모델로 분리했는가?

프로덕션 전 체크

  • □ HTTPS/TLS, 인증, 권한 scope 제한을 모든 endpoint에 적용했는가?
  • □ streaming 끊김 시 Subscribe/Polling fallback이 있는가?
  • □ push webhook SSRF/replay/위조 방어를 구현했는가?
  • □ A2A Inspector/TCK/contract test로 선언 capability를 검증했는가?
  • □ task/artifact 저장소가 재시작·스케일아웃·중복 이벤트에 견디는가?

도입 우선순위

SDK/스펙 변화에 가장 큰 방어막.

2. Agent Registry

여러 agent 연결의 핵심.

3. Task Store

장기 실행과 멀티턴 필수.

4. Streaming

UX 품질을 크게 개선.

분산/비동기 환경에서 필요.

초기에는 선택 사항.

9. 최종 권장 설계

추천: NPM 프로그램에서는 처음부터 “완전한 분산 에이전트 네트워크”를 만들기보다, Host Orchestrator + A2A Client Adapter + Local/Remote Agent Registry를 먼저 만든다. 각 에이전트는 독립 서버로 띄우되, 내부 기능 호출은 MCP 또는 기존 API로 처리한다. 이후 task store, streaming, webhook, 인증을 단계적으로 추가한다.

가장 실용적인 시작점은 다음과 같다.

  1. 내부 타입부터 고정: AgentProfile, AgentTask, AgentArtifact, AgentEvent를 먼저 정의한다.
  2. SDK를 adapter 안에 가둠: @a2a-js/sdk 타입을 앱 전체로 퍼뜨리지 않는다.
  3. Agent Card registry 구축: file/env/well-known/사설 registry 순서로 확장한다.
  4. 라우팅은 deterministic filter + score: LLM 판단만으로 agent를 선택하지 않는다.
  5. v1.0 대응은 별도 브랜치: @a2a-js/sdk@next는 alpha로 검증하고, stable 전환 시 adapter만 수정한다.
