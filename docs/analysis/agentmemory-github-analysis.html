핵심 결론

agentmemory는 단순한 라이브러리가 아니라, iii-sdk 기반 워커와 localhost HTTP, stream, viewer, MCP proxy를 함께 띄우는 독립 메모리 런타임이다. Claude Code, Codex, OpenCode, MCP 클라이언트에서 발생하는 세션/프롬프트/툴 사용 이벤트를 수집하고, 관찰값을 압축해 BM25, 벡터, 그래프 기반 하이브리드 검색으로 다시 제공하는 구조다.

HarnessAgentOS에는 agentmemory를 그대로 붙이는 방식은 권장하지 않는다. 현재 프로젝트의 핵심 제약인 Electron IPC 전용 통신, SQLite WAL 단일 source of truth, 승인 기반 side effect, 사용자 감독형 워크벤치 철학과 충돌한다. 다만 agentmemory의 관찰 수집, 세션 요약, BM25/벡터 검색, pinned slot, provenance/audit, memory benchmark 방식은 Harness-native 기능으로 재해석해 적용할 가치가 크다.

권장 방향은 외부 agentmemory 런타임 통합이 아니라 Harness 내부 SQLite 기반 ObservationMemory/Recall 레이어를 만드는 것이다. 이 레이어는 기존 LearningTrace, ObservationCollector, CapabilityService, LearnerAdvisor를 보강하되, 추천/회상 결과가 사용자의 승인 없이 실행 경로를 바꾸지 않도록 유지해야 한다.

분석 범위와 방법

GitHub 원본 저장소를 얕은 clone으로 받아 코드와 문서를 직접 확인했다. README의 기능 설명만 보지 않고, 실제 entrypoint, function registry, trigger, MCP tool registry, state persistence, hooks, benchmark 문서를 기준으로 런타임 흐름을 재구성했다.

저장소 구조

저장소는 agentmemory 서버, MCP shim, editor/agent hook plugin, 외부 통합 예제, benchmark/eval 도구를 함께 담고 있다. 단일 npm 패키지처럼 보이지만 실제로는 여러 진입점을 가진 제품형 런타임이다.

경로 역할 검토 의견
src/index.ts 메인 agentmemory 서버 entrypoint. iii worker, function registry, triggers, index restore, timers 시작. 실제 제품 핵심. 기능 플래그와 provider fallback이 많이 모이는 중심 파일.
src/cli.ts, src/cli/ 설치, 연결, Codex/Claude/OpenCode hook 설정, 상태 점검 CLI. 사용자 홈 설정 파일을 수정하는 side effect가 많아 승인 UX가 중요하다.
src/functions/ mem::observe, mem::search, mem::context, mem::remember, compression, slots, graph 등 60개 이상 함수. 기능이 풍부하지만 범위가 넓다. Harness에 가져올 때는 기능 단위로 잘라야 한다.
src/triggers/api.ts REST API trigger 등록. 관찰, 검색, context, import/export, health, MCP proxy 등 노출. Harness의 "localhost 서버 금지" 제약과 직접 충돌하는 표면이다.
src/mcp/ MCP tool registry, standalone MCP server, REST proxy/fallback. 도구 모델과 progressive disclosure는 참고 가치가 높다.
src/state/ KV wrapper, schema, BM25 index, vector index, hybrid search, persistence. 검색/인덱싱 설계에서 가장 재사용할 아이디어가 많다.
src/hooks/ Claude/Codex/OpenCode hook 이벤트를 agentmemory REST API로 보냄. 수집 흐름 이해에 중요하지만 Harness에는 hidden hook 자동 주입을 그대로 쓰면 안 된다.
packages/mcp/ @agentmemory/mcp thin npm package. 본체 dist standalone을 실행. Codex MCP 설치 경험을 단순화하기 위한 wrapper다.
plugin/, .codex-plugin/, .claude-plugin/ plugin marketplace metadata, hook manifest, skills. ECC/skills-first 흐름과 유사하지만, Harness 내장 기능으로 흡수하려면 승인 경계를 명확히 해야 한다.
benchmark/, eval/, docs/benchmarks/ synthetic coding-agent-life benchmark, LongMemEval retrieval 평가, 비교 문서. Harness 메모리 기능 도입 시 eval harness의 좋은 참고 자료다.

런타임 아키텍처

agentmemory는 iii-config.yaml의 worker 구성을 바탕으로 HTTP, stream, state, queue, pubsub, cron, observability worker를 띄운다. 기본 포트는 HTTP 3111, stream 3112, viewer 3113이다. 이 구조는 로컬 에이전트들이 같은 메모리 서버를 공유하도록 설계되어 있다. 

agentmemory CLI / hooks / MCP client
        |
        v
localhost REST API :3111  <-->  iii worker registry
        |                         |
        |                         +-- mem::observe
        |                         +-- mem::remember
        |                         +-- mem::search
        |                         +-- mem::context
        |                         +-- mem::summarize
        |                         +-- mem::consolidate-pipeline
        |
        +-- StateKV over iii-state file DB
        +-- BM25 SearchIndex
        +-- optional VectorIndex
        +-- optional GraphRetrieval
        +-- Stream events :3112
        +-- Viewer :3113
        +-- MCP proxy / standalone fallback

시작 흐름

  1. 환경 변수와 config를 읽고 provider fallback, LLM provider, embedding provider를 구성한다.
  2. registerWorker를 호출해 iii worker와 telemetry를 등록한다.
  3. StateKV, MetricsStore, DedupMap, optional VectorIndex를 생성한다.
  4. privacy, observe, compress, search, context, summarize, export/import, graph, lessons, slots 등 mem::* 함수들을 등록한다.
  5. 기능 플래그에 따라 consolidation, team, actions, routines, graph, semantic/procedural memory 함수를 추가 등록한다.
  6. BM25와 vector index를 persisted state에서 복원하고, dimension mismatch가 있으면 vector index를 안전하게 초기화한다.
  7. 필요하면 기존 관찰/메모리에서 index backfill을 수행한다.
  8. REST trigger, MCP endpoints, viewer, auto-forget, lesson decay, consolidation timers를 시작한다.

중요한 점은 agentmemory의 저장소가 HarnessAgentOS처럼 SQLite 도메인 모델을 중심으로 한 애플리케이션 상태가 아니라, iii state worker 위의 scoped key-value store와 별도 index들로 구성된다는 것이다.

Hook 기반 수집 흐름

agentmemory의 가장 실용적인 흐름은 agent hook에서 자동으로 세션 이벤트와 툴 이벤트를 수집하는 부분이다. Claude Code와 Codex에서 다른 hook 이벤트명이 쓰이는 점을 흡수하고, stop/session-end에서 요약과 consolidation을 실행한다.

Hook 동작 주의점
session-start /agentmemory/session/start 호출. 옵션이 켜진 경우 context를 주입한다. 기본은 fire-and-forget에 가깝고 timeout이 짧다. 실패가 사용자 작업을 막지 않도록 설계됐다.
prompt-submit 사용자 prompt를 observation으로 저장한다. 프롬프트 원문에는 민감 정보가 포함될 수 있어 redaction이 중요하다.
pre-tool-use 기본적으로 no-op. context injection 옵션이 켜진 경우 enrich API를 호출한다. 자동 context injection은 Harness의 사용자 감독 철학과 충돌할 수 있다.
post-tool-use 툴명, 입력, 출력, 이미지 참조 등을 observation으로 저장한다. 툴 출력은 길이 제한과 이미지 처리 경로가 있다. 파일/출력 데이터 유출 가능성 검토 필요.
post-tool-failure 실패 정보를 저장하되 interrupt성 실패는 무시한다. 실패 축적은 useful하지만 오류 메시지에 secret이 섞일 수 있다.
stop 세션 요약, end 처리, Codex의 session-end 대체 처리. Codex hook surface 차이를 보정하는 compatibility layer다.
session-end 세션 종료, summary/consolidation/bridge를 실행한다. 백그라운드 지식 생성은 결과 provenance와 사용자 표시가 필요하다. 
prompt/tool event
  -> hook script
  -> REST /agentmemory/observe or session endpoint
  -> api::observe trigger
  -> mem::observe function
  -> stripPrivateData
  -> RawObservation stored in StateKV
  -> stream event published
  -> synthetic or LLM compression
  -> BM25 / vector index update
  -> later context/search/summarize can retrieve it

메모리 저장/검색 흐름

관찰 저장

mem::observe는 agentmemory의 자동 수집 entrypoint다. Hook, REST API, MCP 도구에서 들어온 세션 이벤트를 RawObservation으로 정규화하고, privacy 필터를 거친 뒤 session scoped storage에 저장한다. 이후 compression 결과가 있으면 검색 인덱스에 반영한다.

명시적 기억 저장

mem::remember는 사용자가 직접 저장하는 durable memory 경로다. 입력 validation, Jaccard 기반 supersession, memory id 생성, KV 저장, BM25/vector indexing을 수행한다. 자동 관찰보다 명시성이 높기 때문에 Harness에 도입한다면 이 흐름이 더 안전한 출발점이다.

검색

검색은 세 계층으로 나뉜다. SearchIndex는 자체 BM25 구현으로 stemming, CJK segmenter, synonym, prefix matching, serialization을 제공한다. VectorIndex는 embedding vector를 in-memory map으로 보관하고 cosine similarity로 검색하며, base64 Float32Array persistence와 dimension guard를 갖는다. HybridSearch는 BM25, vector, graph 결과를 Reciprocal Rank Fusion으로 합치고 diversification과 optional rerank를 적용한다. 

memory_smart_search / REST search
  -> mem::smart-search
  -> HybridSearch
     -> BM25 SearchIndex
     -> optional VectorIndex
     -> optional GraphRetrieval
  -> reciprocal rank fusion
  -> session diversification
  -> optional reranker
  -> compact results + lessons
  -> optional expand by ids for full observations

Context 생성

mem::context는 검색 결과를 그대로 던지지 않고, pinned slots, project profile, lessons, summaries, 중요한 observations를 budget 안에서 조합해 XML에 가까운 구조의 context block을 만든다. 이 progressive disclosure 방식은 HarnessAgentOS의 에이전트 handoff와 추천 UX에 적용할 가치가 있다.

Consolidation

mem::summarize는 세션 요약을 만들고, mem::consolidate-pipeline은 요약에서 semantic memory와 procedural memory를 추출한다. reflect tier는 더 높은 수준의 insight를 합성하고, decay는 시간이 지나며 lesson 강도를 낮춘다. Harness에서는 이 과정을 자동 실행하더라도 결과를 UI에 노출하고 사용자가 승인/삭제할 수 있어야 한다.

MCP와 API 표면

src/mcp/tools-registry.ts는 MCP 도구를 core, v040, v050, v051, v061, v070, v073, slots 그룹으로 나눈다. 코드 기준 tool name은 약 56개이며, README의 53/51개류 표현과는 약간 드리프트가 있다. 기본 노출은 essential core 도구 중심이고, AGENTMEMORY_TOOLS=all 설정에서 전체 도구가 보인다.

표면 역할 Harness 적용 판단
REST API observe, remember, search, context, export/import, session, health, MCP proxy. 직접 도입 비권장. Harness는 Express/localhost/WebSocket 서버 추가 금지.
MCP server MCP client가 memory tools를 호출. 서버가 있으면 proxy, 없으면 local fallback. 외부 도구로 연결하는 것은 가능하나 핵심 앱 상태로 쓰면 canonical state가 분리된다.
Standalone fallback agentmemory 서버가 없을 때 in-memory/local fallback으로 일부 도구 제공. 동작 차이가 생기므로 제품 기능으로 신뢰하기 어렵다.
Codex connect ~/.codex/config.toml에 [mcp_servers.agentmemory]를 추가하고 optional hooks를 설치. 사용자 홈 설정 변경이므로 Harness에서는 명시 승인과 rollback UX가 필요하다.
Plugin metadata Claude/Codex plugin marketplace용 manifest와 hook mapping. skills-first 흐름은 참고 가능. Hidden workflow 변경은 피해야 한다.

상태 모델

agentmemory의 src/state/schema.ts는 단일 relational schema가 아니라 여러 scoped KV collection의 계약을 정의한다. 주요 scope는 sessions, observations, memories, summaries, config, metrics, health, embeddings, bm25Index, relations, profiles, graph nodes/edges, semantic/procedural memories, team state, audit, actions, routines, signals, checkpoints, lessons, insights, accessLog, image refs, slots 등이다.

이 방식은 기능 확장에는 빠르지만 HarnessAgentOS의 SQLite WAL source-of-truth 규칙과는 다르다. Harness에서 도입한다면 JSON blob 중심의 KV를 새 canonical state로 만들지 말고, 기존 repository/service 경계 안에서 필요한 테이블을 명시적으로 추가해야 한다.

agentmemory 개념 Harness에 대응 가능한 개념 도입 방식
RawObservation observations, LearningTrace, Artifact 기존 observation 저장소를 확장하고 provenance 필드를 추가.
SessionSummary TaskRun summary, Checkpoint, handoff artifact TaskRun 종료 시 quality evidence와 함께 summary artifact 생성.
Memory / Lesson Learner recommendation, capability note, durable project knowledge 자동 적용이 아니라 추천/검토 대상으로 저장.
BM25 index ObservationMemory lexical index SQLite index table 또는 rebuild 가능한 persisted index metadata.
VectorIndex Optional embedding-backed recall embedding provider/network는 승인 및 설정 UI 뒤에 배치.
Slots Project/user pinned context UI에서 명시적으로 보이고 편집 가능한 pinned context로 구현.

보안 및 개인정보 검토

강점

  • stripPrivateData가 <private> 블록, API key, secret, token, password, Bearer token, OpenAI/GitHub/AWS/Gemini/JWT/npm/GitLab/DigitalOcean 형태의 민감 패턴을 redaction한다.
  • REST/MCP 경로는 AGENTMEMORY_SECRET bearer auth를 지원한다.
  • viewer는 README 기준 CSP와 nonce 기반 보호를 사용한다.
  • import 경로에는 size limit validation이 있고, image compression은 관리 store 밖의 image path 읽기를 거부한다.
  • audit/access log 계층이 있어 durable memory 변경의 provenance를 남길 수 있다.

주의점

  • 기본 secret이 없으면 local REST API가 사실상 보호되지 않을 수 있다. 로컬 앱이라도 다른 프로세스가 접근할 수 있다.
  • localhost HTTP/stream/viewer 포트가 열리므로 HarnessAgentOS의 Electron IPC-only 정책과 충돌한다.
  • hook 기반 자동 수집은 사용자가 인식하지 못한 prompt/tool output 저장으로 이어질 수 있다.
  • compress-file 같은 file-writing 도구는 백업을 만들고 파일을 직접 수정하므로 Harness의 approval gate 없이는 위험하다.
  • import/export/delete/forget류 도구는 데이터 손실과 대량 유출의 위험이 있어 별도 권한 모델이 필요하다.
  • LLM compression과 embedding provider는 외부 API나 로컬 모델로 데이터가 나갈 수 있으므로 provider별 disclosure가 필요하다.

HarnessAgentOS 적용 시에는 agentmemory의 redaction 패턴과 audit 아이디어는 유용하지만, 외부 REST 서버와 hidden hook 자동 저장 방식은 그대로 사용하지 않는 것이 맞다. 저장 전 사용자에게 어떤 범주의 데이터가 durable memory가 되는지 보이고, 삭제/forget UI를 제공해야 한다.

코드 품질 검토

영역 평가
모듈화 기능별 파일 분리는 잘 되어 있지만, src/index.ts에 bootstrapping 책임이 많이 집중되어 있다.
검증 zod와 function-level validation이 많다. 단, API/tool 수가 넓어 validation 일관성을 계속 관리해야 한다.
오류 처리 agent 작업을 방해하지 않기 위해 catch 후 무시하는 경로가 있다. 제품 신뢰성 관점에서는 observability가 부족해질 수 있다.
불변성 actions.ts, lessons.ts, consolidation-pipeline.ts 일부 흐름에 in-place mutation 패턴이 보인다. HarnessAgentOS의 immutability 선호와는 맞지 않는다.
기능 플래그 많은 optional 기능을 env/config로 제어한다. 유연하지만 조합 테스트 부담이 커진다.
문서 드리프트 README의 tool count와 코드상의 registry count가 일부 맞지 않는다. 기능 표면이 빠르게 바뀌는 프로젝트에서 흔한 드리프트다.
테스트 테스트 파일 수와 benchmark harness가 충실하다. 다만 외부 런타임 의존성이 있어 Harness 통합 전에는 별도 contract test가 필요하다.

벤치마크 검토

agentmemory는 단순 README claim에 그치지 않고 synthetic benchmark와 LongMemEval retrieval 문서를 제공한다. 이 점은 강점이다. 다만 두 benchmark 모두 "memory recall/retrieval" 능력의 근거이지, 전체 개발 워크플로우 성공률의 직접 증거는 아니다.

문서 주요 결과 해석
docs/benchmarks/2026-05-20-coding-agent-life-v1.md agentmemory-hybrid P@5 0.578, R@5 0.967, hit rate 15/15, p50 14ms. grep baseline P@5 0.267, R@5 0.967. 작은 fictional corpus에서 ranking precision이 grep보다 좋다는 근거. recall은 둘 다 높아 corpus 특성도 봐야 한다.
benchmark/LONGMEMEVAL.md LongMemEval-S retrieval-only BM25+Vector R@5 95.2%, R@10 98.6%, MRR 88.2. 공식 end-to-end QA score가 아니라 retrieval-only 평가라고 명시되어 있다.
benchmark/COMPARISON.md grep과 agentmemory retrieval 비교 설명. Harness 적용 시에도 grep baseline과 BM25/vector baseline을 함께 둬야 효과를 검증할 수 있다.

HarnessAgentOS에 메모리/회상 기능을 넣는다면 agentmemory의 benchmark style을 차용해 "작업 재개 시 필요한 artifact/decision/approval/quality-gate를 얼마나 정확히 찾는가"를 별도 eval로 측정하는 것이 적절하다.

HarnessAgentOS 적용성

현재 HarnessAgentOS는 사용자가 흐름을 통제하는 감독형 개발 워크벤치다. Renderer는 window.harness.*만 호출하고, Main은 Electron IPC로 서비스에 위임하며, SQLite WAL이 canonical state다. 모든 side effect는 approval을 통과해야 한다. 이 전제를 기준으로 agentmemory의 적용성을 평가하면 다음과 같다.

agentmemory 기능 그대로 도입 Harness-native 도입 판단
localhost REST/stream/viewer 서버 비권장 Electron IPC와 existing renderer route로 재구현 ADR-0002와 충돌한다.
iii StateKV/file DB 비권장 SQLite WAL tables/repositories로 저장 ADR-0003과 충돌한다.
hook 자동 관찰 주의 TaskRun/Step/Approval/Artifact 이벤트에서 명시 관찰 생성 Hidden write가 아니라 앱 내부 이벤트로 처리해야 한다.
BM25 SearchIndex 가능 ObservationMemory lexical index로 이식 가장 적용 가치가 높다.
VectorIndex 조건부 provider 설정/승인 뒤 optional embedding table로 도입 네트워크/모델 경로/비용 disclosure가 필요하다.
HybridSearch/RRF 가능 BM25 + vector + graph/capability signals fusion LearnerAdvisor 추천 품질 개선에 직접 도움이 된다.
Context block 생성 주의 사용자에게 보이는 handoff/recall panel로 생성 자동 prompt injection은 피하고 preview/approval을 둔다.
Slots 가능 Pinned project context로 구현 UI에서 편집/삭제 가능해야 한다.
Consolidation/Lessons 조건부 QualityGate evidence와 연결된 learner note로 저장 자동 정책 변경 금지. 추천으로만 사용.
MCP tool surface 비권장 Harness 내부 service API와 IPC contract로 필요한 subset만 노출 도구가 너무 넓고 side effect가 섞여 있다.

현재 프로젝트에 특히 유용한 아이디어

  • TaskRun과 Step에서 나온 관찰을 나중에 검색 가능한 memory item으로 만드는 ObservationMemory.
  • full output을 매번 넣지 않고 summary, artifact id, provenance를 우선 제공하는 progressive disclosure.
  • BM25와 optional vector를 함께 쓰고 RRF로 합치는 hybrid recall.
  • 프로젝트별 반복 규칙이나 사용자가 고정한 결정을 보관하는 pinned context slot.
  • 세션 종료 시 다음 실행을 위한 handoff summary를 생성하는 흐름.
  • 메모리 기능 자체를 평가하는 recall benchmark harness.
  • redaction, audit, source/provenance 필드를 durable memory의 필수 필드로 두는 방식.

그대로 가져오면 안 되는 부분

  • Harness 앱 안에 agentmemory의 HTTP/stream/viewer 서버를 추가하는 방식.
  • iii StateKV나 JSON/KV blob을 Harness의 새로운 canonical state로 삼는 방식.
  • 사용자가 보지 못하는 hook에서 prompt/tool output을 지속 저장하는 방식.
  • 검색 결과를 자동으로 agent prompt에 삽입해 실행 경로를 바꾸는 방식.
  • 파일 쓰기, import/export, forget/delete 도구를 approval 없이 노출하는 방식.
  • 외부 embedding/LLM provider로 데이터를 보내는 것을 기본값으로 만드는 방식.

권장 적용 계획

HarnessAgentOS에 적용한다면 작은 단계로 들어가야 한다. 먼저 외부 provider 없이 deterministic lexical recall을 만들고, 이후 사용자가 명시적으로 선택한 경우에만 vector/LLM consolidation을 추가하는 순서가 안전하다.

단계 구현 범위 검증 기준
Phase A SQLite 기반 memory_observations 또는 기존 observations 확장. source type, taskRunId, stepId, artifactId, redactedText, summary, tags, createdAt, provenance 저장. repository unit test, migration idempotency, sensitive token redaction test.
Phase B BM25 lexical index 또는 rebuild 가능한 token table 추가. TaskRun detail에서 "관련 이전 관찰"을 조회. known corpus에서 top-K recall test, rebuild test, CJK query test.
Phase C LearnerAdvisor/CapabilityService가 memory recall 결과를 추천 이유로 참조하되 자동 실행은 하지 않음. 추천 결과에 evidence id가 표시되고 hidden route change가 없는지 IPC test.
Phase D Pinned context slot UI. 사용자가 프로젝트 규칙/결정을 고정, 수정, 삭제할 수 있게 함. renderer event subscription, preload API, approval/visibility UX test.
Phase E Optional embedding provider와 vector table. provider 설정, 비용/데이터 disclosure, dimension guard 포함. provider off 기본값, dimension mismatch reset/backfill test, no-network mode test.
Phase F Memory recall benchmark. generated project handoff, approval, quality gate, artifact retrieval을 측정. grep baseline 대비 precision/recall 개선 수치와 regression threshold.

구체적 backlog 후보

  1. packages/core/src/types/memory-observation.ts에 observation memory 계약 추가.
  2. packages/storage에 memory observation repository와 idempotent migration 추가.
  3. packages/learner에 ObservationRecallService 추가, 처음에는 BM25 lexical만 사용.
  4. apps/desktop/electron/ipc에 recall IPC domain 추가. 9-layer IPC 규칙 준수.
  5. Renderer에 "관련 근거" panel을 추가하되, recommendation/capability 실행 경로를 자동 변경하지 않음.
  6. 민감 정보 redaction 테스트를 먼저 작성하고 통과 후 저장 로직 구현.
  7. TaskRun 종료 시 handoff summary artifact를 생성하되, QualityGate evidence와 연결.
