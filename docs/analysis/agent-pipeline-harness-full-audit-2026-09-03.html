6. 성능 분석

관점증거평가
Hot pathimport, binding save, profile delete, seed migration은 cold path. Worker wave 실행은 warm/hot 경계.실행 루프에는 새 DB 조회나 lock을 추가하지 않음.
Allocation / copyHarness draft 검증은 step map + visiting/visited set을 한 번 구성. Pipeline 최대 step 수는 20.O(V+E), bounded allocation. JSON parse는 canonical DB trust boundary에서 필요한 단일 materialization.
CPU / dispatch삭제 reverse lookup은 SQLite json_each 한 번이며 현재 binding set 5개.드문 관리 작업에서 JS 전체 row materialization을 피함. 실행 dispatch에는 영향 없음.
Concurrency / latency새 background task, queue, timer, lock 없음. readiness는 호출 로컬 map만 사용.contention/backpressure 변화 없음. 예상 tail-latency 영향은 무시 가능한 cold-path 범위.
추론: 위 성능 평가는 코드 경로와 bounded workload에 근거합니다. 실제 provider latency·token 비용·대규모 production DB p95/p99는 이번 로컬 smoke가 측정하는 대상이 아닙니다.
