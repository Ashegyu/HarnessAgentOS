CodeGraph 분석 및 HarnessAgentOS 적용성 검토

colbymchenry/codegraph의 코드 구조, 인덱싱 흐름, MCP/CLI 표면, 성능상 장단점을 확인하고 현재 HarnessAgentOS에 적용할 수 있는 방식을 검토했다. 결론은 직접 내장보다 외부 MCP/CLI로 먼저 사용해 검증하는 편이 가장 낮은 위험과 높은 실익을 가진다는 것이다.

대상 프로젝트 HarnessAgentOS

1. 결론

추천: CodeGraph는 HarnessAgentOS에 바로 내장하지 말고, 별도 MCP/CLI로 먼저 사용한다. 현재 프로젝트에는 이미 MCP 서버 등록, per-agent profile binding, CLI invocation 준비 경로가 있다. CodeGraph는 그 위에 붙이면 코드 이해, 영향 범위 분석, 호출 관계 추적, 관련 컨텍스트 검색 기능을 즉시 실험할 수 있다.

CodeGraph는 Tree-sitter 기반 AST 추출, SQLite 그래프 저장소, FTS5 검색, 참조 해석, MCP 도구, CLI를 함께 제공한다. HarnessAgentOS의 현재 RepoIndexService는 파일 요약, 심볼, import 정도를 저장하는 경량 인덱스이므로 역할이 다르다. CodeGraph는 이 경량 인덱스를 대체하기보다, 리뷰/설계/영향 분석 에이전트가 필요할 때 호출하는 외부 지식 그래프 도구로 두는 편이 안전하다.

직접 내장은 보류가 맞다. CodeGraph는 자체 .codegraph/codegraph.db, 파일락, 워커 스레드, 파일 감시, Tree-sitter WASM 런타임, Node 버전 제약을 가진다. HarnessAgentOS의 source of truth는 SQLite WAL 기반 storage 계층이고, side effect는 approval을 거쳐야 한다. 따라서 내부 저장소/런타임으로 합치면 운영 복잡도와 latency 예측 불확실성이 커진다.

2. 범위와 증거 기준

구분 내용
Evidence GitHub 공개 소스의 src/index.ts, src/types.ts, src/db/schema.sql, src/extraction/index.ts, src/resolution/index.ts, src/context/index.ts, src/graph/traversal.ts, src/mcp/tools.ts, src/bin/codegraph.ts, src/sync/index.ts를 확인했다. HarnessAgentOS 로컬 파일도 packages/agent, packages/core, packages/storage, apps/desktop/electron 중심으로 확인했다.
Inference 성능 효과, 컨텍스트 품질 개선, latency 영향은 코드 구조와 현재 HarnessAgentOS 호출 경로를 근거로 추정했다. 실제 수치는 로컬 인덱싱/쿼리 벤치마크 전까지 확정할 수 없다.
Uncertainty 현재 머신의 Node 버전, CodeGraph npm 배포 버전, HarnessAgentOS 실제 대형 워크로드, 워커 스레드와 Electron 개발 서버 동시 실행 영향은 이 문서 작성 시점에 측정하지 않았다.

3. CodeGraph 코드 구조 요약

CodeGraph
  ├─ DatabaseConnection / QueryBuilder
  ├─ ExtractionOrchestrator
  │   ├─ git ls-files 우선 스캔
  │   ├─ Tree-sitter WASM 파서
  │   ├─ worker thread 파싱
  │   └─ files, nodes, edges, unresolved_refs 저장
  ├─ ReferenceResolver
  │   ├─ import/path/name 기반 참조 해석
  │   ├─ framework-specific rule
  │   ├─ bounded LRU cache
  │   └─ unresolved refs -> graph edges
  ├─ GraphQueryManager / GraphTraverser
  │   ├─ callers, callees, impact, path, type hierarchy
  │   └─ batched neighbor query
  ├─ ContextBuilder
  │   ├─ natural-language symbol extraction
  │   ├─ exact/prefix/text/camel-case search
  │   └─ source block + relation context assembly
  ├─ MCP tools
  │   ├─ codegraph_context
  │   ├─ codegraph_search / node / trace / explore
  │   └─ codegraph_callers / callees / impact / status / files
  └─ CLI
      ├─ init / index / sync / status
      ├─ query / context / callers / callees / impact / affected
      └─ serve --mcp
파일 역할 HarnessAgentOS 관점
src/index.ts 공개 CodeGraph 클래스. init/open/close, index/sync/watch, query, traversal, context, optimize/clear/destroy를 묶는 facade. 라이브러리로 직접 내장하면 lifecycle과 side effect 경계가 커진다. 외부 MCP 프로세스로 두면 격리된다.
src/types.ts node kind, edge kind, language, graph/context/task 타입 정의. 언어 범위가 TypeScript, JavaScript, Python, Go, Rust, Java, C#, Kotlin 등으로 넓다. HarnessAgentOS는 TypeScript 중심이지만, 향후 다중 repo 분석에는 유리하다.
src/db/schema.sql nodes, edges, files, unresolved_refs, FTS5 nodes_fts, 다수의 조회 인덱스와 트리거. 자체 DB를 쓰므로 HarnessAgentOS canonical state와 섞지 않는 것이 안전하다.
src/extraction/index.ts git 기반 스캔, ignore 처리, 파일 크기 제한, worker thread 파싱, Tree-sitter grammar 로딩, 변경 파일 판별, 추출 결과 저장. 현재 RepoIndexService보다 무겁지만 의미론적 그래프를 만든다. cold/warm 작업으로 분리해야 한다.
src/resolution/index.ts unresolved reference를 import/name/framework rule로 edge로 해석. cache, batch, built-in/external filtering 포함. call/reference graph 품질을 좌우한다. 정확도는 언어와 프로젝트 패턴별 검증이 필요하다.
src/context/index.ts 자연어 쿼리에서 관련 심볼과 소스 블록을 조합해 컨텍스트를 만든다. 기본 output size는 제한적이다. HarnessAgentOS의 context-packer보다 에이전트 컨텍스트 품질을 높일 가능성이 크다.
src/graph/traversal.ts BFS/DFS, callers/callees/call graph/type hierarchy/usages/path/impact radius. neighbor batch fetch로 N+1을 줄인다. 리뷰, 영향 분석, phase plan 검증에서 직접적인 가치가 있다.
src/mcp/tools.ts MCP 도구 정의와 입력/출력 제한, projectPath 기반 cross-project query, status, explore, trace 제공. 현재 HarnessAgentOS MCP 등록 구조와 가장 잘 맞는 표면이다.
src/bin/codegraph.ts CLI 명령과 serve --mcp. install/uninstall/init/index/sync/status/context/query/impact/affected 제공. 처음에는 CLI 파일럿으로 정확도와 latency를 확인하고, 이후 MCP profile에 연결하는 순서가 적합하다.

4. 데이터 모델과 조회 특성

CodeGraph의 핵심 저장소는 SQLite 그래프다. files가 파일 단위 상태를 들고, nodes가 심볼/구조 요소를 들며, edges가 contains, calls, imports, extends, implements, references 같은 관계를 저장한다. unresolved_refs는 파싱 시점에 아직 target을 모르는 참조를 보관하고, resolver가 이를 실제 edge로 변환한다.

저장 요소 관찰한 설계 성능상 의미
Nodes kind, name, qualified_name, file path, line range, language 등으로 인덱싱된다. 심볼명 기반 조회, 파일/언어별 필터링, line 기반 탐색이 빠르게 설계되어 있다.
Edges source/kind, target/kind, provenance index가 있다. callers/callees/impact 같은 graph traversal에서 반복 조회 비용을 낮추려는 구조다.
FTS5 nodes_fts와 트리거로 text search를 지원한다. 자연어/부분 검색을 일반 LIKE scan보다 낫게 처리할 수 있다.
Unresolved refs 대상 미확정 참조를 batch로 해결하고, 해결 후 삭제한다. 추출과 해석을 분리해 indexing latency를 단계화한다.
HarnessAgentOS에 직접 저장하지 않는 편이 낫다. 현재 프로젝트의 canonical state는 storage 패키지의 SQLite WAL이다. CodeGraph DB는 분석 캐시로 보고, 삭제/재생성 가능한 외부 산출물로 취급해야 한다.

5. MCP와 CLI 표면

MCP 도구

  • codegraph_context: 자연어 작업 설명을 기반으로 관련 코드와 관계를 반환하는 주 도구.
  • codegraph_search: 심볼/파일 검색.
  • codegraph_node: 특정 노드의 정의, trail, callers/callees 조회.
  • codegraph_trace: 두 지점 사이의 관계 경로 탐색.
  • codegraph_impact: 변경 영향 범위 탐색.
  • codegraph_files, codegraph_status: 파일 목록과 인덱스 상태 확인.

CLI 명령

  • init, index, sync, status: 인덱스 생명주기.
  • context, query: 질의 기반 컨텍스트 검색.
  • callers, callees, impact: 그래프 질의.
  • affected: 변경된 소스에서 영향받는 테스트 추론.
  • serve --mcp: MCP 서버 실행.

HarnessAgentOS에는 이미 MCP 서버 타입, stdio/http/sse transport, per-agent profile binding, Codex/Claude용 MCP config 생성 경로가 있다. CodeGraph는 secret이 필요 없는 stdio MCP로 보이며, mcp-config-builder의 Codex stdio 제약에도 맞는다.

6. HarnessAgentOS 현재 구조와 비교

현재 HarnessAgentOS repo context 흐름

TaskRun
  → AgentPlanningService.generatePlan(...)
  → getRepoContext(taskRun, prompt)
  → RepoIndexService / repo_index_files
  → context-packer.ts
  → agent-prompt-builder.ts
  → CLI agent invocation

현재 MCP 흐름

MCP server definition
  → mcp-config-builder.ts
  → prepareMcpInvocation(...)
  → Claude .mcp.json 또는 Codex -c override
  → agent profile별 tool surface
현재 파일 확인 내용 CodeGraph와의 관계
packages/agent/src/repo-index-service.ts 파일 스캔, 경량 요약, regex 기반 symbol/import 추출, read cap과 max file limit을 둔다. 빠른 map 용도. CodeGraph는 AST/graph 기반 deep context 용도.
packages/storage/src/repositories/repo-index-repository.ts repo_index_files에 symbols/imports JSON을 저장한다. CodeGraph schema와 병합하지 않는 편이 안전하다.
packages/agent/src/context-packer.ts prompt tokens와 path/summary/symbol/import 매칭으로 상위 파일을 선택하고, map-only라는 주석성 안내를 붙인다. CodeGraph의 codegraph_context가 보완할 수 있는 가장 직접적인 지점이다.
packages/agent/src/mcp-config-builder.ts Claude와 Codex용 MCP 설정을 생성한다. Codex는 stdio만 지원하며 secret vault 참조를 거부한다. CodeGraph는 stdio, no-secret 방식으로 붙이기 좋다.
apps/desktop/electron/ipc/mcp-ipc.ts renderer에서 MCP 서버 draft, scaffold, profile binding을 IPC로 관리한다. UI에서 CodeGraph 서버를 등록하고 특정 profile에만 바인딩하는 방식이 자연스럽다.

7. Hot-path 평가

경로 Hot/Warm/Cold 근거 권장 처리
HarnessAgentOS renderer IPC와 TaskRun 상태 갱신 Hot 사용자 조작과 화면 갱신에 직접 연결된다. CodeGraph 호출을 이 경로에 동기적으로 넣지 않는다.
Agent plan 생성 전 repo context 구성 Warm agent invocation 전에 실행되며 체감 latency에 영향을 준다. 기본 경량 인덱스는 유지하고, profile/작업 유형에 따라 CodeGraph MCP를 선택적으로 쓰게 한다.
CodeGraph 최초 index Cold Tree-sitter parsing, DB write, reference resolution이 포함된다. 명시적 approval 후 별도 작업으로 실행한다. UI hot path와 분리한다.
CodeGraph context/query Warm SQLite/FTS/traversal 조회이며 prompt 준비 중 사용될 수 있다. timeout, output cap, profile gating을 둔다.
CodeGraph watch/sync Warm 파일 변화에 따라 백그라운드 I/O와 parsing이 발생할 수 있다. 파일럿 초기에는 watch를 끄고 수동 sync로 운영한다.
성능 판단은 아직 측정 전이다. CodeGraph 코드에는 worker thread, batch query, output cap, cache, file size limit 같은 방어 장치가 있다. 다만 현재 프로젝트에서 p50/p95 latency, indexing 시간, DB 크기, agent prompt 품질 개선 폭은 별도 측정이 필요하다.

8. 적용 가능성 판단

선택지 판단 이유
외부 CLI로 수동 사용 권장 설치, index, context, impact 명령만으로 즉시 검증 가능하다. 프로젝트 코드 변경이 필요 없다.
HarnessAgentOS MCP 서버로 등록 권장 현재 MCP profile binding 구조와 잘 맞는다. reviewer/architect/perf agent에 선택적으로 노출할 수 있다.
기존 RepoIndexService 보완재로 사용 조건부 권장 경량 인덱스는 계속 prompt map으로 쓰고, CodeGraph는 deep query에만 사용하면 latency와 복잡도를 통제할 수 있다.
RepoIndexService를 CodeGraph로 교체 비권장 storage schema, side effect approval, DB lifecycle, Node/WASM runtime까지 영향을 준다. 현재 이득 대비 변경 폭이 크다.
CodeGraph 라이브러리 직접 내장 보류 파일락, watcher, 워커, DB, cleanup 책임이 앱 내부로 들어온다. 충분한 pilot evidence 이후 별도 adapter로 검토해야 한다.

9. 별도 사용 방법

다음 순서는 HarnessAgentOS 코드를 바꾸지 않고 CodeGraph를 독립 분석 도구로 사용하는 방식이다. 최초 init, index, sync는 파일/DB side effect가 있으므로 명시적으로 실행한다.

# 3. 전체 인덱싱

# 4. 상태 확인

# 5. 자연어 컨텍스트 검색
codegraph context "AgentPlanningService가 repo context와 MCP 설정을 CLI invocation에 연결하는 흐름" --path "C:\Users\GC\Desktop\Works\Personal\Study\HarnessAgentOS"

# 6. 영향 범위 분석 예시
codegraph impact "RepoIndexFile" --path "C:\Users\GC\Desktop\Works\Personal\Study\HarnessAgentOS"

10. 장점

  • 코드 이해 품질 개선: 단순 파일 요약이 아니라 AST node와 edge를 기반으로 관련 코드를 찾는다.
  • 영향 범위 분석: callers/callees/impact/path query로 public API 변경, IPC 계약 변경, storage schema 변경 전 검토가 쉬워진다.
  • MCP 친화성: HarnessAgentOS의 MCP profile binding과 직접 맞물린다. 특정 agent에만 노출할 수 있다.
  • 다중 언어 확장성: TypeScript 외에도 C#, Python, Go, Rust 등 여러 언어 parser kind를 정의한다.
  • 출력 통제: MCP 도구에 max output, input length, path length 제한이 있어 agent prompt 폭주를 줄이려는 설계가 보인다.
  • 변경 추적 가능성: git 기반 changed-file 감지와 affected test 분석은 phase 검증 workflow에 활용할 수 있다.

11. 리스크와 완화

리스크 영향 완화책
최초 인덱싱 비용 CPU, I/O, DB write가 발생한다. approval 후 수동 실행. UI hot path와 분리. 인덱싱 시간과 DB 크기를 측정한다.
watcher 백그라운드 작업 latency 변동과 파일 시스템 부하가 생길 수 있다. 초기에는 watch 비활성, 수동 sync 사용.
Node/WASM 버전 제약 CLI 실행 실패 또는 parser crash 가능성이 있다. node --version, codegraph status를 pilot checklist에 포함한다.
그래프 정확도 불확실성 동적 import, Electron IPC, generated code, framework convention에서 누락 가능성이 있다. 대표 흐름 5개를 수동 ground truth와 비교한다.
중복 인덱스 저장소 HarnessAgentOS storage와 CodeGraph DB가 별도로 존재한다. CodeGraph DB는 재생성 가능한 cache로 정의하고 canonical state로 취급하지 않는다.
agent tool overuse 불필요한 MCP 호출로 응답 지연이 커질 수 있다. profile gating, prompt rule, timeout, output cap을 설정한다.

12. 권장 최소 구현 계획

  1. Phase 0: 외부 CLI 파일럿. CodeGraph를 설치하고 HarnessAgentOS 루트에서 init, index, status, context, impact를 실행한다. 이 단계는 프로젝트 코드 변경 없이 진행한다.
  2. Phase 1: MCP 서버 등록. HarnessAgentOS UI에서 stdio MCP 서버로 등록하고 reviewer/architect/performance profile에만 바인딩한다.
  3. Phase 2: agent 운영 규칙 추가. call path, impact, IPC/storage 변경 검토 작업에서 CodeGraph MCP를 먼저 사용하도록 profile prompt 또는 운영 문서에 추가한다.
  4. Phase 3: 품질 측정. 대표 작업 5개에서 기존 repo context만 쓴 결과와 CodeGraph context를 함께 쓴 결과를 비교한다.
  5. Phase 4: adapter 검토. 파일럿 결과가 좋을 때만 packages/agent에 optional CodeGraphContextProvider adapter를 설계한다. storage migration은 하지 않는다.

14. 바로 적용 가능한 HarnessAgentOS 개선 아이디어

CodeGraph 자체를 내장하지 않더라도 다음 아이디어는 낮은 위험으로 참고할 수 있다.

  • RepoIndexService ignore 목록 보강: CodeGraph처럼 build/cache/output directory 기본 ignore를 더 명시적으로 관리한다.
  • git-aware scan option: 전체 파일 스캔 전에 git tracked files를 우선 사용하는 옵션을 검토한다. 단, git이 없는 workspace fallback은 유지한다.
  • agent context tool policy: architecture/review/perf profile에는 context 도구를 우선 사용하도록 하고, implementer profile에는 필요 시에만 허용한다.
  • output budget 규칙: CodeGraph MCP의 max output/input cap처럼 HarnessAgentOS 자체 generated context도 명시적 budget과 truncation reason을 남긴다.
  • affected test workflow: CodeGraph의 affected 개념을 참고해, 변경 파일에서 관련 테스트 후보를 제안하는 advisory 기능을 별도 phase로 검토한다.
구현 우선순위 지금 당장 코드를 바꾼다면 MCP 등록 preset 또는 운영 문서 추가가 최우선이다. RepoIndexService 교체나 AST 인덱싱 내장은 측정 전에는 추천하지 않는다.
