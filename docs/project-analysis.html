사용자 감독형 로컬 개발 워크벤치의 현재 구조와 위험

HarnessAgentOS는 Electron·React·SQLite 위에서 계획, 승인, 실행, 산출물, 품질 게이트를 하나의 감사 가능한 TaskRun으로 연결한다. 현재 구조적 방향은 일관되지만, 작업 트리가 매우 큰 변경 상태이고 opt-in 직접 쓰기 및 host shell의 잔여 보안 경계가 있어 “검증 완료”가 아니라 “리뷰 가능한 현재 스냅샷”으로 판단해야 한다.

1. 분석 범위와 방법

repo-scan의 standard-depth 절차를 수동 적용했다. Git 추적/미추적 표면을 분류하고, 각 모듈의 대표 구현과 계약 문서를 읽고, 현재 diff와 최근 커밋을 교차 확인했다.

포함

  • apps/desktop, 9개 packages/*, docs
  • 현재 HEAD와 보고서 작성 직전 Git 상태
  • Electron 경계, DB canonical state, 승인/Runner, 품질, agent/orchestration
  • 대표 소스의 정적 계약과 선택된 정책 테스트

제외 또는 제한

  • node_modules, 빌드/패키징 산출물, .git 내부
  • 실제 Codex/A2A/MCP 원격 호출과 자격 증명 경로
  • 전체 테스트, Electron GUI E2E, 설치본 smoke, 성능 벤치마크
  • 의존성 취약점 감사 및 운영 환경 장애 주입

수치는 현재 파일 시스템 및 Git 출력에서 산출했다. 기존 사용자 변경은 읽기만 했으며 이 보고서 외 파일은 수정하지 않았다.

2. 핵심 아키텍처

주요 경계는 코드에서 확인된다. BrowserWindow는 Node 통합을 끄고 context isolation과 sandbox를 켜며, preload가 제한된 window.harness.* API를 노출하고, main의 IPC 계층이 서비스와 SQLite 상태를 연결한다.

RendererReact workbench. 파일·SQL·process 대신 window.harness.* 사용.
PreloadcontextBridge 기반 typed IPC surface. raw ipcRenderer 비노출.
Electron Main22개 IPC 도메인을 등록하고 도메인 서비스를 조합.
Services / Runners승인 정책, agent, orchestration, file/shell/git/test, quality.
SQLite WALschema v40, 33개 canonical table, artifact·approval·trace 저장.
상태 흐름: 사용자 입력 → Thread → TaskRun → Step → Checkpoint → Approval → Runner → Artifact → QualityGate → ready_for_review → 사용자 markDone. Main은 events:taskRunChanged를 push하고 renderer는 fresh detail을 다시 pull한다.

확인된 강점

  • packages/core에서 @harness/storage 실제 import 없음.
  • 추적 파일에 금지된 .test.ts/.test.tsx 없음.
  • SQLite open 시 WAL, foreign key, 5초 busy timeout 강제.
  • 승인 revision과 실행 claim이 DB 조건부 UPDATE로 묶임.
  • 실경로 기반 junction/symlink containment가 file runner에 적용됨.

설계상 중요한 경계

  • JSON column은 상태 직렬화 수단이며 canonical store는 SQLite다.
  • QualityEvaluator는 증거를 판정하고 TaskRun 전이는 completion service가 담당한다.
  • shell/file_delete는 global/profile auto consent 대상에서 제외된다.
  • Codex workspace-write는 기본값 false인 별도 opt-in 실행 모드다.

4. 주요 기능

대화 중심 TaskRun

Thread 연속성, follow-up anchor, 상태 전이, timeline과 fresh-state pull을 결합한다.

근거: core task-run types

승인 우선 실행

9개 action type을 정책 평가하고 revision, 승인 snapshot, 단일 실행 claim으로 변경 후 재승인과 중복 실행을 통제한다.

근거: approval repository

파일·CLI Runner

file write/patch/delete, shell, git, test를 artifact와 step에 연결한다. Windows npm/batch 처리와 출력 decoding이 분리되어 있다.

근거: RunnerService

증거 기반 품질 게이트

테스트·빌드·smoke·diff artifact를 판정하며 읽기 전용 요청의 변경과 change 요청의 diff 부재를 탐지한다.

근거: QualityEvaluator

Codex agent 실행

비대화형 CLI, provider 탐색, invocation queue, timeout/stall, strict JSON v1 output, post-hoc workspace diff 증거를 제공한다.

근거: AgentPlanningService

Pipeline과 A2A

worker wave, role/profile binding, handoff, repair/backflow와 원격 A2A endpoint routing을 지원한다.

근거: orchestration worker runner

Capability와 Learner

skill source를 capability로 색인하고 observation/instinct/learning trace에서 모델 및 topology 추천을 만든다.

근거: LearnerAdvisor

운영 표면

Settings, agent profile, MCP, secrets, diagnostics, budget/cost, eval, backup, notification, package 관리가 workbench에 통합된다.

근거: WorkbenchShell

5. 변경 현황

현재 HEAD는 2026-09-03의 feat(workbench): Codex 5.6 에이전트 운영 통합이며, 그 이후 작업 트리에는 127개 추적 파일 수정(+4,852/-630)과 41개 미추적 경로가 있다. 아래는 파일명과 diff를 기준으로 묶은 현재 작업 흐름이다.

승인·CLI 안전성 v40

approval revision/approved snapshot, DB 실행 claim, file recycle-bin delete, Windows command resolution·encoding·cancellation이 추가 또는 강화되고 있다. 이전 검수에서 제기된 승인 후 내용 변경과 중복 실행 문제는 현재 소스 및 선택 테스트에서 보완 근거가 확인된다.

Task contract와 strict agent output

answer/review/diagnose/research/change 의도별 side-effect 및 web-search 제약, JSON schema v1, non-interactive questions 비허용, Codex stream parsing과 read-only preflight가 작업 중이다.

자동 품질·완료 UX

automatic quality service, task response quality, evidence reader, quality requirement 모델, answer copy/clipboard, task completion E2E가 추가되고 있다.

모델 예산·profile·orchestration 확장

model allocation/usage estimator, budget policy, topology advisor, worker wave/handoff, harness package, A2A repository가 동시에 변경 중이다.

Workbench 현지화와 복구 경로

i18n, CLI 재탐색, provider executable/process tree 관리, 설정/승인/우측 패널과 관련 E2E가 추가되고 있다.

6. 발견된 위험

아래는 현재 소스와 Git 상태에서 재확인한 위험이다. 버튼으로 심각도를 필터링할 수 있다.

High 168개 기존 변경 경로의 통합 불확실성

127개 추적 수정과 41개 미추적 파일이 여러 계층을 동시에 바꾼다. HEAD만으로 재현되지 않으며 일부 핵심 구현과 테스트가 아직 미추적이어서 리뷰·백업·bisect의 신뢰도가 낮다.

근거: git status --porcelain, git diff --numstat

High workspace-write의 사전 승인 경계 차이

설정이 켜지면 change TaskRun의 Codex가 직접 파일을 쓸 수 있고 시스템은 post-hoc workspace change evidence를 수집한다. 기본값은 false지만, 이 모드는 Runner의 승인→실행→artifact-before-write 의미와 동일하지 않다.

근거: AgentPlanningService sandbox 선택·tracker

High host shell은 OS sandbox가 아님

shell은 수동 승인과 위험 토큰 차단을 거치지만 실행 프로세스의 파일·네트워크 권한을 OS 수준에서 제한하지 않는다. 명령 분류 정규식과 secret masking은 tripwire이며 완전한 보안 경계가 아니다.

근거: runner policy 및 task-contract 주석

Medium 파일 I/O의 잔여 TOCTOU

실경로 containment와 승인 preimage 비교가 추가되었지만 검사와 실제 write/trash 사이를 원자적으로 묶지는 못한다. delete 구현도 host trash API에 atomic compare-and-delete가 없음을 명시한다.

근거: FileDeleteRunner 재검증 주석

Medium IPC 계약 확장에 따른 drift 비용

22개 IPC 도메인과 큰 preload/main 조합이 core API, handler, registration, preload, window typing을 함께 바꿔야 한다. 현재처럼 37개 desktop 파일이 동시에 변할 때 한 계층 누락 가능성이 커진다.

근거: IPC_CHANNELS 및 preload/main

Medium 단일 provider 정책과 확장 포맷의 불일치

현재 AgentProvider와 profile 검증은 codex만 허용하지만 문서/타입 일부는 claude source format과 provider hint를 유지하고 A2A routing을 별도로 제공한다. 호환 레이어와 실제 실행 provider의 경계를 계속 명시해야 한다.

근거: AgentProvider와 harness-package types

Medium 검증 결과의 시점·환경 분산

2026-09-07/08 검수 문서의 전체 테스트·E2E 수가 서로 다르고 현재 worktree는 다시 변경되었다. 이번 실행에서도 공식 npm 경로가 PATH에 없어 대체 경로를 사용했다. 결과를 하나의 “전체 통과”로 합치면 안 된다.

근거: 최근 검수 문서와 이번 명령 출력

Low package-managed 의존성의 별도 감사 필요

embedded vendor 디렉터리는 발견하지 못했지만 Electron, better-sqlite3, Playwright 등 native/runtime 의존성의 취약점·ABI·라이선스 검증은 이번 범위에 없다.

근거: package manifests, tracked-path inventory

7. 실제 검증과 미검증의 구분

같은 “검증”이라도 현재 실행, 과거 artifact, 정적 확인은 서로 대체하지 않는다.

이번 실행에서 확인

  • Git HEAD/branch/status와 변경량 집계
  • 740 tracked, 240 test files, 모듈별 파일 표면
  • 11개 tsconfig의 tsc --noEmit 모두 exit 0
  • 선택 정책 테스트 72/72 통과
  • Node v24.18.0, schema v40, 33 table, 22 IPC domain
  • core→storage import 없음, 금지 테스트 확장자 없음
  • embedded vendor 계열 추적 경로 없음

부분/대체 경로

  • shell PATH에 node/npm이 없어 공식 npm run check는 시작 실패
  • typecheck는 Electron의 Node 모드로 tsc를 각 config에 직접 실행
  • tsx가 uv_os_get_passwd ENOMEM으로 실패해 임시 in-process geteuid shim 후 선택 테스트 실행
  • 2026-09-07/08 전체 테스트·E2E 결과는 문서 증거이며 이번에 재실행하지 않음

이번에 미검증

  • 공식 npm run test/verify/build
  • 전체 240개 테스트 파일과 coverage
  • Electron GUI 전체 E2E 및 clipboard 실제 OS round-trip
  • 실제 Codex/MCP/A2A provider 호출
  • packaged EXE 설치/업데이트/복구
  • dependency audit, 서명, 라이선스 준수
  • 대규모 repo index·stream 성능과 장시간 안정성
선택 테스트 명령의 경계: agent output schema, auto-approve, completion, approval concurrency, path containment/secret masking을 대상으로 72개가 통과했다. 이는 Runner 전체, DB migration 전체, desktop UI 또는 실제 CLI 성공을 증명하지 않는다.
