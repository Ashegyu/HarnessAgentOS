MCP와 Skill 사용 및 자동 생성 구현 설계

HarnessAgentOS에서 MCP 서버와 Agent Skill을 어떻게 구분해서 쓰고, 각 AgentProfile에 어떤 MCP와 Skill을 선언하며, 사용자가 승인한 범위 안에서 MCP/Skill을 자동 생성하도록 확장하는 설계다. 현재 문서는 구현 전 설계 산출물이며, 런타임 코드 변경은 포함하지 않는다.

1. 결론

핵심 결정: MCP와 Skill은 같은 "에이전트 능력"이 아니다. MCP는 실행 가능한 외부 도구 서버이고, Skill은 절차와 지식을 점진적으로 로드하는 capability package다. HarnessAgentOS에서는 둘 다 AgentProfile에 선언하되, 실제 실행은 기존 Approval, Runner, Artifact, QualityGate 경계를 통과해야 한다.

항목 결정 이유
MCP 사용 AgentProfile.mcpServerIds와 McpServerConfig.scope로 선언 이미 저장소에 per-agent/global MCP 선택 구조와 per-invocation 임시 config 생성 경로가 있다.
Skill 사용 SkillSource 스캔, Capability 추천, capability_use 승인 후 prompt context로 주입 Skill은 자동 실행자가 아니라 사용자가 볼 수 있는 추천/지식 계층이라는 기존 아키텍처와 맞다.
Agent별 선언 기존 AgentProfile을 선언 단위로 유지하고, 최소 확장으로 required/optional 의미만 보강 새 테이블부터 만들면 현재 Settings, storage, IPC와 중복된다. 먼저 기존 필드를 명시적으로 해석한다.
자동 생성 생성은 "파일 작성"이 아니라 preview → approval proposal → materialize → refresh/bind 흐름 저장소의 핵심 제약인 side effect 승인 모델을 보존한다.
Codex MCP 현재는 설계상 보류. Claude CLI만 실제 --mcp-config 적용 경로로 취급 코드가 Codex MCP 인자 형식을 아직 검증하지 않았고, prepareMcpInvocation이 Codex provider에서 null을 반환한다.

2. 조사 요약

2.1 MCP 공식 문서에서 확인한 기준

근거 설계 반영
MCP는 host, client, server 구조이며 host가 서버별 client connection을 관리한다. transport는 stdio와 Streamable HTTP가 핵심이다. MCP Architecture HarnessAgentOS는 main process가 MCP config를 합성하고 CLI invocation에 넘기는 host-side control point를 유지한다. renderer는 MCP process나 credential에 접근하지 않는다.
MCP server primitive는 Tools, Resources, Prompts다. Tools는 모델이 호출할 수 있는 실행 함수이고, Resources는 context 데이터, Prompts는 사용자 제어형 템플릿이다. MCP Server Concepts 자동 생성은 "모든 것을 tool로 감싸기"가 아니라 tool/resource/prompt 분류를 먼저 수행한다. 실행 side effect가 있는 기능만 tool 후보로 둔다.
MCP tools는 schema-defined interface이며, user consent와 activity log를 통한 oversight가 권장된다. MCP Tools MCP tool 사용은 AgentProfile의 allow/deny policy와 Harness approval ledger에 맞춰 표시되어야 한다. 생성된 MCP tool schema는 짧고 명확해야 하며 tool call 결과는 artifact로 남긴다.
MCP roots는 filesystem scope를 알려주는 coordination mechanism이며, 보안 경계 자체는 아니다. MCP Client Concepts 자동 생성 MCP가 roots를 사용하더라도 실제 쓰기/실행 제한은 Harness path policy와 approval/runner에서 강제한다.
stdio MCP server는 stdout에 일반 로그를 쓰면 JSON-RPC stream이 깨진다. 공식 가이드는 stderr logging을 권장한다. Build an MCP Server MCP scaffold generator는 stdout logging 금지 lint와 smoke probe를 포함해야 한다.

2.2 Agent Skill 문서에서 확인한 기준

근거 설계 반영
Anthropic Agent Skills는 SKILL.md, scripts, references, templates 등을 가진 filesystem package이며, Skill metadata는 startup에, instructions는 trigger 시점에, resources는 필요할 때 로드한다. Claude Agent Skills HarnessAgentOS의 SkillLoader와 CapabilityService는 metadata-first, instruction-on-demand 방식을 유지한다.
Agent Skills open format은 필수 SKILL.md와 optional scripts/, references/, assets/ 구조를 정의하고, progressive loading을 요구한다. Agent Skills Specification 자동 생성 Skill은 최소 name, description, body를 만들고, 추가 자료는 필요할 때만 references/templates/examples로 분리한다.
MCP 공식 사이트도 MCP server build를 Agent Skill로 보조하는 방식을 소개한다. Build with Agent Skills MCP 자동 생성 자체도 하나의 Harness Skill 또는 built-in capability로 표현할 수 있다. 즉, generator는 hidden hook이 아니라 사용자에게 보이는 capability다.
OpenAI Codex repository의 sample Skill은 Skill 안에서 필요한 MCP server를 우선 사용하도록 안내하는 패턴을 보여준다. Codex sample SKILL.md Skill과 MCP는 경쟁 관계가 아니라 조합 관계다. Skill은 "언제, 왜, 어떤 MCP tool을 쓰는지"를 설명할 수 있다.

2.3 조사에서 얻은 운영 원칙

  • MCP는 실행 표면이다. 외부 시스템 호출, 파일/DB/API 작업, live context retrieval처럼 protocol boundary가 필요한 일에 쓴다.
  • Skill은 판단 표면이다. 절차, 팀 규칙, 반복 workflow, MCP tool 사용법, 검증 checklist를 담는다.
  • Skill이 MCP를 지정할 수 있다. 예를 들어 openai-docs Skill은 OpenAI docs MCP를 우선 쓰라고 지시할 수 있다.
  • MCP roots는 보안 경계가 아니다. Harness 쪽 path policy, approval, runner sandbox가 실제 경계다.
  • 자동 생성은 반드시 review-first여야 한다. 생성된 Skill/MCP는 미리보기와 검증을 거친 뒤 사용자가 승인해야 저장된다.

3. 현재 구현 근거

영역 관련 파일 확인된 사실
AgentProfile packages/core/src/types/agent-profile.ts mcpServerIds, skillSourceIds, permissions.allowedSkillIds, toolAllowlist, toolDenylist, budget가 이미 있다.
MCP registry packages/core/src/types/mcp.ts, packages/storage/src/repositories/mcp-server-repository.ts MCP server는 stdio, http, sse transport와 global/per-agent scope를 가진 row로 저장된다.
MCP invocation apps/desktop/electron/main.ts, packages/agent/src/mcp-config-builder.ts main process가 enabled global MCP와 profile-bound per-agent MCP를 합쳐 임시 .json config를 만들고, invocation 뒤 삭제한다. SecretVault key는 spawn 직전에만 복호화된다.
MCP provider 제한 apps/desktop/electron/main.ts, packages/agent/src/model-cli-types.ts 현재 코드상 Codex provider는 MCP config file을 만들지 않는다. 주석상 Codex --mcp-config 검증이 보류되어 있다.
Skill loading packages/skillify-adapter/src/skill-loader.ts <root>/<skill>/SKILL.md를 읽고 frontmatter를 metadata로 파싱한다. instruction과 resources는 별도 함수로 on-demand load된다.
Skill approval packages/skillify-adapter/src/capability-service.ts 추천 Skill은 capability_use approval candidate로 제안되고, 승인된 capability만 prompt context에 들어간다. skill_script 실행도 직접 실행이 아니라 approval row를 만든다.
Skill authoring apps/desktop/electron/ipc/skill-source-ipc.ts, packages/core/src/types/skill-source.ts previewSkillDraft와 proposeSkillFile이 이미 있다. 자동 생성 Skill은 이 흐름을 재사용하는 것이 가장 작다.
설계상 유리한 점: 저장소는 이미 MCP registry, per-agent profile binding, Skill source authoring, capability approval, prompt injection 지점을 갖고 있다. 따라서 이번 기능은 새 agent runtime이 아니라 기존 선언/승인 모델을 완성하는 일에 가깝다.

4. MCP와 Skill 사용 기준

4.1 MCP를 써야 하는 경우

  • 외부 API, DB, GitHub, Jira, 문서 저장소, 로컬 indexing server처럼 runtime I/O가 필요하다.
  • 모델이 typed input schema에 맞춰 반복 호출해야 한다.
  • 결과가 최신 상태, 외부 시스템 상태, filesystem 상태에 의존한다.
  • 도구 호출 결과를 activity log, artifact, health check로 관리해야 한다.
  • credential, OAuth, token, endpoint 설정이 필요하다.

4.2 Skill을 써야 하는 경우

  • 팀 규칙, 리뷰 절차, 설계 방식, 검증 checklist처럼 절차 지식이 핵심이다.
  • 반복되는 프롬프트/작업 흐름을 짧은 metadata로 발견하고 필요할 때만 instruction을 읽으면 된다.
  • script가 있더라도 실행보다 사용법과 판단 기준이 더 중요하다.
  • 특정 MCP tool을 언제 쓰는지 지시하고 싶다.
  • 새 코드 없이 문서와 예시만으로 agent 품질을 높일 수 있다.

4.3 결정 매트릭스

요구 권장 표면 예시
현재 repo의 테스트 명령과 convention 안내 Skill test-runner/SKILL.md, harness-workflows/SKILL.md
로컬 문서 index 검색과 chunk 읽기 MCP manual_search, manual_read_chunk 같은 typed tool
OpenAI API 최신 문서 확인 Skill + MCP Skill이 "OpenAI docs MCP를 우선 사용"하도록 지시
보안 리뷰 절차와 체크리스트 Skill reviewer profile에 security skill source와 allowed skill id 선언
GitHub issue/PR 조회, label 변경 MCP credential과 action audit가 필요한 외부 tool
프로젝트별 MCP 서버 scaffold 생성 Skill로 절차화하고, 생성 결과는 approval된 file_write build-mcp-server style skill + Harness file proposal

5. Agent별 MCP/Skill 선언 모델

5.1 목표

사용자는 "planner는 설계 Skill만, performance reviewer는 성능 Skill과 성능 MCP만, coder는 repo-aware MCP와 patch Skill만"처럼 에이전트별 도구/지식 표면을 선언할 수 있어야 한다. 이 선언은 실제 실행 권한과 분리되어야 하며, 선언되어도 자동 실행이 보장되면 안 된다.

5.2 기존 필드를 선언 계약으로 재정의

필드 선언 의미 런타임 의미
AgentProfile.mcpServerIds 이 profile에서 사용할 수 있는 per-agent MCP server id 목록 Claude invocation 때 global MCP + 이 목록의 enabled MCP만 임시 config에 포함
AgentProfile.skillSourceIds 이 profile에 노출할 Skill source 목록. 비어 있으면 trusted global source만 Capability suggestion 후보 scope를 제한하는 데 사용
permissions.allowedSkillIds 특정 Skill만 허용하는 whitelist. 비어 있으면 enabled skill 전체 후보 추천과 capability_use approval 후보 생성 전에 filter
permissions.toolAllowlist MCP tool name allow pattern MCP client/tool-call event 수집이 가능해지는 시점에 tool 사용 정책 검증
permissions.toolDenylist MCP tool name deny pattern allowlist보다 우선. UI에서도 "이 profile에서 차단" 표시

5.3 선언 예시

{
  "id": "ap_performance_reviewer",
  "name": "Performance Reviewer",
  "role": "performance-reviewer",
  "mcpServerIds": ["mcp_repo_index", "mcp_benchmark_results"],
  "skillSourceIds": ["skillify_project", "skillify_user"],
  "permissions": {
    "autoApproveActions": [],
    "blockedActions": ["file_write", "dependency_install", "git_commit"],
    "allowedSkillIds": ["csharp-performance-review", "benchmark-plan"],
    "toolAllowlist": ["repo_*", "benchmark_*"],
    "toolDenylist": ["*_write", "*_delete"]
  }
}

5.4 필요한 최소 보강

현재 AgentProfile은 source id와 server id를 저장하지만, "필수로 포함되어야 하는 Skill", "추천만 할 Skill", "자동 생성 후보" 같은 의도는 표현하지 못한다. 첫 구현은 public type churn을 줄이기 위해 AgentProfile에 바로 새 필드를 추가하지 않고, AgentCapabilityPolicy를 settings UI와 proposal artifact에서만 사용한다. 

export interface AgentCapabilityPolicyDraft {
  profileId: string;
  requiredMcpServerIds: readonly string[];
  optionalMcpServerIds: readonly string[];
  requiredSkillIds: readonly string[];
  optionalSkillIds: readonly string[];
  deniedToolPatterns: readonly string[];
  notes: string;
}

승인 후 실제 저장은 기존 AgentProfile.mcpServerIds, skillSourceIds, permissions.allowedSkillIds, toolAllowlist, toolDenylist에 반영한다. 나중에 required/optional semantics가 런타임에 필요하다고 검증되면 별도 migration을 추가한다.

6. 자동 생성 설계

6.1 자동 생성의 범위

생성 대상 1차 범위 비범위
Skill SKILL.md 초안, frontmatter, body, references/templates/examples 목록 승인 없는 파일 쓰기, untrusted source 자동 trust 승격, script 자동 실행
MCP server config 기존 외부 MCP 등록 초안, command/url/envSecretRefs, healthCheck 계획 사용자 secret 값 자동 추출, global config 직접 수정, Codex 미검증 플래그 적용
MCP server scaffold 작은 local stdio TypeScript server scaffold proposal, tool schema, smoke test script 대형 API wrapper 전체 생성, OAuth 완성, remote deploy 자동화
Agent binding AgentProfile에 연결할 MCP/Skill 후보와 allow/deny pattern 제안 사용자 확인 없는 profile update, hidden routing change

6.2 자동 생성 입력

export interface CapabilityGenerationRequest {
  taskRunId: string;
  targetDir: string;
  userIntent: string;
  targetKind: "skill" | "mcp_config" | "mcp_scaffold" | "agent_binding";
  profileIds: readonly string[];
  sourceId?: string;
  evidenceArtifactIds: readonly string[];
}

6.3 생성 파이프라인

User request -> classify generation target -> inspect current AgentProfile / MCP / SkillSource / Capability registry -> draft structured proposal -> static validation -> preview response (artifact storage optional) -> approval proposal -> user approves -> materialize file or update row -> refresh registry or health-check MCP -> bind to AgentProfile when explicitly approved -> record artifact and LearningTrace

6.4 Skill 자동 생성 흐름

Skill 생성은 이미 있는 skillSource.previewSkillDraft와 skillSource.proposeSkillFile을 재사용한다. generator는 SkillAuthorDraft를 만들 뿐 파일을 직접 쓰지 않는다. 

export interface GeneratedSkillDraft {
  sourceId: string;
  slug: string;
  name: string;
  description: string;
  triggerTerms: string[];
  riskLevel: "low" | "medium" | "high";
  allowedActions: ApprovalActionType[];
  body: string;
  recommendedProfileIds: string[];
  rationale: string;
}
  1. generator가 task intent와 repo evidence를 바탕으로 GeneratedSkillDraft를 만든다.
  2. IPC handler가 이를 SkillAuthorDraft로 변환해 previewSkillDraft validation을 통과시킨다.
  3. 현재 MVP는 preview 결과를 IPC 응답으로 반환해 사용자에게 보여준다. 별도 preview artifact 저장은 후속 확장으로 둔다.
  4. 사용자가 승인하면 proposeSkillFile로 file_write approval을 만든다.
  5. 승인된 runner 실행 뒤 skillSource.refresh로 capability registry를 갱신한다.
  6. profile binding은 별도 approval로 처리한다. Skill 파일 생성과 profile 변경을 한 approval에 섞지 않는다.

6.5 MCP config 자동 생성 흐름

MCP config 생성은 "새 MCP 서버를 구현"하는 것과 "이미 존재하는 MCP 서버를 등록"하는 것을 분리한다. 1차 구현은 등록 초안 생성에 집중한다. 

export interface GeneratedMcpServerDraft extends McpServerConfigDraft {
  recommendedProfileIds: string[];
  secretPlaceholders: string[];
  rationale: string;
}

export interface McpServerDraftPreview {
  ok: boolean;
  errors: McpServerDraftPreviewIssue[];
  warnings: string[];
  server: McpServerConfigDraft;
  wouldNameCollide: boolean;
  sanitizedConfigKey: string;
}

export interface McpServerConfigDraft {
  name: string;
  description: string;
  transport: "stdio" | "http" | "sse";
  command?: string;
  args?: string[];
  url?: string;
  env: Record<string, string>;
  envSecretRefs: Record<string, string>;
  scope: "global" | "per-agent";
  enabled: boolean;
}
  1. generator는 plain secret 값을 만들지 않는다. 필요한 secret은 envSecretRefs key 이름만 제안한다.
  2. 사용자는 UI에서 secret vault에 값을 저장하거나 기존 key를 선택한다.
  3. mcp.generateServerDraft는 저장/파일쓰기/probe 없이 초안과 preview warning만 반환한다.
  4. mcp.upsert 전 validation과 duplicate name check를 실행한다.
  5. mcp.healthCheck가 성공하면 profile binding 후보를 보여준다.
  6. 실패하면 row는 disabled 상태로 저장하거나 저장 자체를 보류한다.
  7. Codex MCP config 전달은 현재 보류 상태다. 생성/preview 문구와 실제 적용 경계는 Claude --mcp-config로 한정한다.

6.6 MCP scaffold 자동 생성 흐름

1차 구현에서는 제한적으로만 허용: local stdio TypeScript scaffold만 생성한다. remote HTTP/SSE, OAuth, 대형 API wrapper는 설계 문서와 TODO만 만든다.

scaffold generator는 MCP 공식 문서 기준을 반영해 stdout logging 금지, @modelcontextprotocol/sdk 사용, typed schema, smoke probe를 포함해야 한다. 

mcp-server-name/
  package.json
  tsconfig.json
  src/index.ts
  README.md
  tests/smoke.test.mjs

생성된 scaffold는 targetDir 아래에 바로 쓰지 않고 approval 대상 file proposal 묶음으로 만든다.

export interface GeneratedFileProposal {
  path: string;
  content: string;
  rationale: string;
  riskLevel: "low" | "medium" | "high";
}

6.7 Agent binding 자동 생성 흐름

binding generator는 생성된 Skill/MCP를 어떤 AgentProfile에 연결할지 추천한다. 예를 들어 performance 관련 Skill은 performance-reviewer, build 복구 MCP는 build-error-resolver에 추천한다. 

export interface CapabilityBindingProposal {
  profileId: string;
  addMcpServerIds: string[];
  addSkillSourceIds: string[];
  allowSkillIds: string[];
  addToolAllowPatterns: string[];
  addToolDenyPatterns: string[];
  rationale: string;
  risk: "low" | "medium" | "high";
}

적용은 agents.update를 호출하는 설정 변경 approval로 분리한다. 이 분리는 "Skill 파일 생성 성공"과 "Agent profile 정책 변경"을 독립적으로 rollback하거나 reject할 수 있게 한다.

7.3 저장소 설계

MVP는 새 테이블 없이 Artifact와 Approval.proposedAction을 사용해도 된다. 다만 재시도/감사/비교가 중요해지면 아래 테이블을 추가한다. 

CREATE TABLE IF NOT EXISTS capability_generation_runs (
  id TEXT PRIMARY KEY,
  task_run_id TEXT NOT NULL,
  target_kind TEXT NOT NULL,
  status TEXT NOT NULL,
  request_json TEXT NOT NULL,
  draft_json TEXT,
  preview_json TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY(task_run_id) REFERENCES task_runs(id)
);

JSON column은 repository 규칙에 맞춰 _json suffix를 사용한다. canonical workflow state는 SQLite row이며, 파일 JSON은 source of truth가 아니다.

9. 보안, 승인, 비용 정책

9.1 승인 정책

작업 승인 요구 비고
Skill draft preview 승인 불필요 파일 쓰기 없음. validation만 수행
Skill file materialize file_write approval 필요 proposeSkillFile 경로 재사용
MCP config row upsert settings update approval 권장 초기 MVP에서 직접 settings UI 저장이면 명시 save action으로 대체 가능
MCP scaffold file 생성 file_write approval 필요 현재 MVP는 Runner의 단일 filePatch 계약을 보존해 파일별 approval을 생성하고, 추후 bundle proposal로 확장
MCP health check 사용자 명시 실행 또는 safe read-only probe stdio spawn이 발생하므로 UI에서 실행 대상 command를 보여준다.
Skill script 실행 skill_script approval 필요 untrusted source는 실행 차단

9.2 자동 생성 제한

  • 생성된 MCP server는 기본 enabled=false 또는 health success 전 profile binding 금지로 시작한다.
  • secret 값은 생성하지 않는다. 필요한 key 이름만 제안하고 SecretVault 입력은 사용자가 한다.
  • MCP tool description에는 hidden instruction이나 prompt injection성 문구를 허용하지 않는다.
  • Skill body에는 "approval 우회", "사용자에게 숨김", "무조건 실행" 같은 금지 표현을 validation warning으로 잡는다.
  • AgentProfile의 toolDenylist는 allowlist보다 우선한다.
  • 생성된 Skill/MCP는 사용자가 profile에 명시적으로 bind하기 전까지 기본 agent prompt에 들어가지 않는다.

9.3 토큰과 latency 정책

MCP와 Skill은 등록 수보다 "노출되는 schema 크기", "tool/resource response 크기", "Skill instruction 로드 시점"이 비용에 더 크게 영향을 준다. 따라서 generator는 다음 원칙을 지킨다.

  • MCP tool은 작은 수의 high-signal tool로 시작한다. 대형 API wrapper는 자동 생성하지 않는다.
  • tool response는 기본 summary, path, top N, limit을 지원한다.
  • Skill metadata description은 짧고 구체적으로 만든다.
  • Skill references는 body에 길게 붙이지 않고 별도 파일로 분리한다.
  • 성능/비용 sensitive profile은 AgentPermissions.budget과 profile tuning에 연결한다.

11. 검증 계획

11.1 단위 테스트

  • GeneratedSkillDraft → SkillAuthorDraft 변환과 frontmatter validation
  • Skill body 금지 표현 warning
  • MCP config draft transport별 validation
  • secret placeholder가 없을 때 healthCheck 또는 enable 차단
  • AgentProfile binding proposal이 기존 ids를 중복 추가하지 않음
  • tool deny pattern이 allow pattern보다 우선함

11.2 통합 테스트

  • Skill 자동 생성 preview는 파일을 쓰지 않는다.
  • Skill 생성 approval 승인 전에는 CapabilityRegistry.refresh 결과가 바뀌지 않는다.
  • 승인 후 생성된 Skill이 capability list에 표시된다.
  • MCP global + per-agent selection이 buildClaudeMcpConfig 입력에 올바르게 반영된다.
  • Codex provider invocation은 MCP config path를 받지 않는다.
  • MCP temp config file은 invocation 종료 후 삭제된다.

11.3 수동 검증

  1. Settings에서 새 Skill source를 추가하되 trusted=false로 둔다.
  2. Capability Authoring Wizard로 code-review Skill draft를 만든다.
  3. preview에서 trigger terms, risk, allowed actions를 확인한다.
  4. approval 전 실제 파일이 없는지 확인한다.
  5. approval 실행 후 skillSource.refresh 결과에 새 Skill이 포함되는지 확인한다.
  6. 특정 reviewer AgentProfile에 새 Skill을 bind한다.
  7. 새 TaskRun에서 capability 후보가 표시되지만 자동 실행되지 않는지 확인한다.
  8. 테스트용 stdio MCP를 등록하고 healthCheck 성공 후 Claude profile에 bind한다.
  9. Claude invocation에서 "MCP 설정 준비 완료" progress가 보이고, Codex profile에서는 경고 또는 "활성 MCP 설정 없음"이 보이는지 확인한다.

12.1 남은 불확실성

  • Codex CLI의 현재 MCP config 인자 지원 여부는 별도 실측이 필요하다.
  • MCP tool allow/deny를 실제 tool call 직전에서 강제하려면 CLI가 tool-call event를 충분히 노출하는지 확인해야 한다.
  • remote HTTP/SSE MCP의 auth 방식은 provider별 차이가 크므로 MVP에서는 config 등록과 healthCheck까지만 다룬다.
  • Skill open format은 빠르게 확장 중이므로 Harness 내부 frontmatter는 portable 최소 필드와 Harness-specific 확장 필드를 분리해야 한다.

12.2 최종 설계 판정

현재 저장소 구조에서는 P2 Skill 자동 생성을 먼저 구현하는 것이 가장 작고 안전하다. 이미 preview/propose 경로가 있고, MCP처럼 외부 process spawn이나 credential 문제가 없다. 그 다음 P1 Agent 선언 UI를 정리하고, P3 MCP config 생성으로 확장하는 순서가 적합하다.
