Pipeline × Thread Binding 실행 계획

파이프라인은 사용자가 명시적으로 원할 때만 거치도록 하고, 그 선택을 스레드 생성 시점에 한 번만 받는다. 본 문서는 그 변경에 필요한 모든 파일·필드·테스트를 두 페이즈로 나누어 기술한다.

1. 현재 아키텍처 요약

채팅 입력은 두 갈래로 흐른다:

ConversationInput.submit() │ ├──▶ orchExpanded == false ─▶ agent.generatePlan(taskRunId) │ └─ settings.activeAgentProfileId 1개의 │ AgentProfile.persona/tuning 사용 │ (파이프라인 무관) │ └──▶ orchExpanded == true ──▶ orchestration.draftPlan({taskRunId, mode, pipelineId}) └─ pipeline.steps → WorkerStep[] 생성 사용자가 plan approval 승인 후 WorkerRunner.runApproved() └─ 결정적 stub 텍스트 반환 (실제 에이전트 호출 없음)

결과적으로 사용자가 "이 스레드는 X 파이프라인으로 처리되었으면 좋겠다"고 표현할 단일 지점이 없다. 매 메시지마다 ▸ Orchestration 토글을 켜야 하고, 켜도 출력은 하드코딩된 stub이다.

2. Phase 1 — 스레드 단위 파이프라인 바인딩

Phase 1 스레드에 pipelineId를 부여하고 채팅 라우팅을 자동화한다. 출력 품질은 다루지 않는다.

2.7 Phase 1의 한계 (명시적)

이 페이즈만 적용하면 사용자가 파이프라인 바인딩된 스레드에서 메시지를 보내도 worker-runner는 여전히 결정적 stub 텍스트를 반환한다. UX 경로만 정리되고, 출력 품질 개선은 Phase 2의 몫이다.

3. Phase 2 — Worker가 실제 에이전트를 호출

Phase 2 WorkerRunner의 결정적 stub을 제거하고 각 step에서 AgentProfile의 persona/tuning으로 실제 CLI를 호출한다.

3.1 (선결) Approval 정책 결정

현재 worker-runner.ts 헤더 주석은:

"if the worker suggests a side-effecting action it MUST be persisted as a separate approval — never executed directly here."

Phase 2에서 worker가 진짜 에이전트를 호출하면 그 에이전트는 file_write/shell 같은 side-effect를 제안할 수 있다. 다음 중 하나를 코딩 시작 전에 정해야 한다:

  • (a) Side-effect-free worker. worker는 텍스트 결과(log artifact)만 생성. 제안된 액션이 있으면 별도 approval로 큐잉. 일반 채팅과 동등한 안전 모델.
  • (b) Plan approval이 worker 액션까지 위임. orchestration_plan approval을 승인하면 그 안의 worker가 만드는 모든 후속 approval이 자동 승인된다. settings.approval.autoApprove의 캐스케이드 동작과 일관됨.

(a)가 보수적 기본값. (b)를 원하면 autoApprove 플래그처럼 명시적 opt-in으로 둘 것.

3.4 WorkerRunner 의존성 주입

packages/orchestration/src/worker-runner.ts

export interface WorkerRunnerDeps {
  state: LocalStateService;
  agentPlanning: AgentPlanningService;  // ⬅ 신규
}

// runWorkerStepBody (이전: 동기, 하드코딩 텍스트)
// 이후: async, 실제 CLI 호출
private async runWorkerStepBody(
  step: WorkerStep,
  profile: AgentProfile | null,
  taskRunId: string,
): Promise {
  if (!profile) {
    // 레거시 mode-driven plan: 결정적 텍스트 유지 (백워드 호환)
    return roleBody(step.role);
  }
  const result = await this.deps.agentPlanning.invokeForWorker({
    taskRunId,
    profile,
    userRequest: step.instruction,
    // profile.tuning, profile.cli, profile.mcpServerIds 모두 사용
  });
  return result.outputText;
}

AgentPlanningService는 이미 generatePlan으로 활성 프로필 기반 CLI 호출을 한다. Phase 2는 동일 로직을 "특정 프로필 + 명시적 instruction"으로 호출하는 진입점(invokeForWorker 또는 동등)을 추가하는 일.

4. 실행 순서 및 백워드 호환성

4.1 권장 순서

  1. Phase 1 먼저. 스레드 옵션 + 라우팅 단순화. 출력은 stub 그대로지만 UX는 완성됨. 이 시점에 PR 단위로 끊고 사용자가 실제 동작을 검증.
  2. Approval 정책 결정. §3.1의 (a) vs (b)를 사용자가 선택 — 코드 작성 전에 명시적으로 확정.
  3. Phase 2 구현. WorkerStep.instruction 추가 → planner 갱신 → WorkerRunner 리팩터 → 테스트 교체.
  4. Phase 2 검증. Phase 1에서 만든 파이프라인 바인딩 스레드에 메시지 보냈을 때 실제 페르소나가 반영되는지 확인.

4.2 백워드 호환성

대상호환 처리
기존 스레드 행 (pipeline_id NULL)"파이프라인 없음" → 일반 채팅. 영향 없음.
기존 orchestration plan artifact (instruction 필드 없음)runApproved에서 step.instruction ?? step.inputSummary로 폴백.
기존 worker artifact (하드코딩 텍스트)읽기 전용. 새 worker 호출이 새 artifact를 생성하므로 영향 없음.
레거시 mode-driven plan (agentProfileId 없는 step)Phase 2에서도 결정적 텍스트 유지 (profile == null 분기).
참조하던 pipeline이 삭제된 threadUI에서 "(파이프라인 없음)"으로 표시, 실제 라우팅은 일반 채팅으로 폴백.

4.3 마이그레이션 안전성

  • 스키마 변경은 ALTER TABLE ... ADD COLUMN ... NULL 한 줄. 기존 데이터 손실 없음.
  • SCHEMA_VERSION bump가 멱등 — 재실행해도 NOOP.
  • Phase 1 / Phase 2 사이에 사용자가 앱을 빌드해도 깨지지 않음 — Phase 1은 stub을 그대로 호출.

5. 실제 구현과의 차이 및 Follow-up

5.1 계획서 대비 변경 사항

항목계획서실제 구현이유
WorkerStep.instruction 필수 string 옵셔널 string? v12 이전 plan artifact JSON에는 instruction 필드가 없다. 옵셔널로 두고 runner에서 inputSummary 폴백을 처리해 레거시 plan 행도 안전하게 실행.
WorkerRunner.deps.agentPlanning 필수 주입 옵셔널 (WorkerCliInvoker?) tests가 {state}만으로 runner를 생성하는 기존 패턴을 그대로 유지. 미주입 시 Phase 7 결정적 stub 폴백.
새 인터페이스 이름 (언급 없음) WorkerCliInvoker orchestration 패키지가 agent 전체에 의존하지 않도록 좁은 인터페이스만 노출. AgentPlanningService.invokeForWorker 가 구조적으로 만족.
agent_invocations 행 생성 계획서에 명시 없음 worker 호출에서는 생성 안 함 cost/latency 추적은 follow-up. worker는 step + log artifact만 만들고, 합성 invocationId를 큐 동시성용으로만 사용.
main.ts 생성 순서 (언급 없음) agentPlanning 먼저, 그 다음 OrchestrationService 의존성 방향이 OrchestrationService → agentPlanning으로 바뀌어 기존 순서가 깨졌다. orchEnabledBySettings 클로저는 그대로 작동.
"+ 새 스레드" 다이얼로그 별도 다이얼로그 mockup 기존 ThreadSidebar 인라인 폼에 Pipeline 드롭다운 추가 현재 코드의 인라인 폼이 잘 동작하고 있어 굳이 다이얼로그로 분리할 필요 없음.

5.2 Approval 정책 (a) Side-effect-free 의 운영상 의미

Phase 2의 invokeForWorker는 정책 (a)에 따라 file_write / shell / dependency_install / git_commit / network 같은 액션을 실행하지 않는다. 모델 출력에 그런 액션 제안이 텍스트로 들어와도 현재는 단순히 worker artifact의 본문으로만 저장된다. action approval로 변환·큐잉하는 흐름은 follow-up이다.

5.3 알려진 Follow-up

우선순위항목설명
중 Worker invocation cost/latency 추적 agent_invocations 행 + prompt artifact를 worker 호출에서도 생성해 RuntimeStatusBar와 finance 리포트가 워커 비용도 반영하게 만든다.
중 Action 제안 → 별도 approval 큐잉 모델이 출력 텍스트에서 제안한 file_write/shell을 파싱해 action_type approval로 큐잉. 정책 (a)의 자연스러운 확장.
저 스레드 헤더 배지 + 파이프라인 정의 팝오버 현재는 사이드바 행과 ConversationInput 위에만 배지가 있다. WorkbenchShell 상단 헤더에도 표시하고 클릭 시 파이프라인 step 목록 팝오버를 띄우면 디스커버리가 좋아진다.
저 스레드 생성 후 pipelineId 변경 UI 현재는 생성 시 한 번만 선택 가능. 스레드 detail 패널에서 "Pipeline 변경" 액션을 노출하면 사용자가 스레드를 새로 만들지 않고도 라우팅을 바꿀 수 있다. UpdateThreadInput.pipelineId는 이미 지원함.
저 ConversationInput 토글 코드 제거 현재는 unbound 스레드를 위해 ▸ Orchestration 토글 + Legacy mode 드롭다운 코드가 남아 있다. 사용자가 unbound 스레드에서도 thread 단위 바인딩만 사용하면 토글 자체를 제거해 코드 단순화 가능.

본 문서는 advisor 리뷰를 반영해 작성되었으며, 양 페이즈가 실제 코드 변경으로 완료된 후 §5 가 추가되었다.
