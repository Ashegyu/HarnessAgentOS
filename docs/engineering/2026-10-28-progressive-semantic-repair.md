# 첫 보정 뒤 드러난 추가 의미 오류의 실행 기반 재보정

후속 [첫 보정부터 두 번째 보정까지 실제 모델 검증](2026-10-28-full-live-semantic-repair.md)에서 첫 patch도 실제 모델로 생성하는 전체 경로를 확인했다. 아래 이전 실행의 점수와 stub 사용 사실은 당시 기록 그대로 유지한다.

## 원인과 변경

직전 비교에서는 학습 전 LeasePool 검사가 취소 관찰 타이밍을 보정한 뒤 `Generation == 0`이라는 다른 잘못된 단정을 드러냈다. 추가 정상 구현은 실패했으나 평가 정책이 컴파일 오류에만 두 번째 보정을 허용했다. 또한 실제 제출 diff가 이미 있는 동일 품질 상태에서는 서로 다른 실패라도 같은 checker/종료 코드 때문에 기존 반복 실패 차단기에 걸릴 수 있었다. 테스트 준비 단계의 diff 유무가 바뀌면 이 결함이 가려졌으므로 실제 평가와 같은 제출 상태에서 재현했다.

호스트가 정상 기준 실패를 관측하면 등록 기준 집합 fingerprint·실패한 기준 index·실패 종류·진단으로 식별값을 만든다. 컴파일 실패는 분리된 build의 제한된 오류 코드/등록 경로/정확한 메시지를 사용하고, runtime은 실제 stderr의 제한된 `Unhandled exception` type/message를 사용한다. 스택의 임시 경로·행 번호, checker 소스 변경, 실행/기록 ID는 식별값에 넣지 않는다. 인식하지 못한 runtime 출력은 같은 기준의 동일한 실패로 보수적으로 취급한다. 이 값은 **관측한 실패의 구분**이며 서로 다른 근본 원인을 증명하지 않는다.

식별값은 SQLite 스키마 46의 `validation_runs.failure_fingerprint`에 기록한다. 이미 연결된 승인 회귀 실행의 실제 실패와 result artifact가 있어야 기록 가능하며, 취소·입력 변경·일반 shell·후보만의 실패에는 새 식별을 부여하지 않는다. 실행 결과는 terminal 이후 수정할 수 없다. migration은 nullable column 추가이며 기존 행 보존과 재적용을 검증했다.

반복 시도 예약은 caller의 임의 hash 대신 각 gate에 연결된 불변 실행 증거를 트랜잭션 안에서 다시 읽는다. 비교하는 양쪽의 실패 실행 모두에 상세 식별이 있어야 세부 진단을 구분한다. 과거 상세 정보가 없으면 기존 비교로 보수적으로 차단한다. 버전 변경이나 새로운 artifact만으로 시도 횟수를 얻지 못하도록 했다. TaskRun의 기본 보정 상한 2회, pending 승인, 현재 입력/품질 증거 확인, 후보 불변과 이미 채택된 검사 보호는 유지했다.

## 비교 조건과 예산

실제 모델 실행 소스는 **03ca709**으로 고정했다. 이전과 같은 학습 3사례, 두 평가 문제, 조건별 각 문제 두 번, 최초 요청·코드·정상 구현 집합·미사용 정상 변형·모델 `gpt-5.6-sol / medium`·시간 제한·도구 금지·원래 숨겨진 검사와 결함 변형을 유지한다. 배점도 기존 구현 60점 + 검사 40점이다. 두 번째 보정에 의미 오류를 허용하는 정책만 양쪽에 동일하게 추가한다.

최초 8회, 총 호출 최대 **16회**, 조건별 보정 최대 **4회**, 답안별 보정 최대 **2회**다. 모든 최초 생성과 1차 보정을 먼저 진행하고, 남은 해당 조건 예산만 2차 보정에 사용한다. 다른 조건의 남은 예산을 가져오거나 모든 예산을 소진하기 위한 호출을 만들지 않는다. 후보만의 실패는 검사 보정 대상으로 삼지 않는다.

다른 답안이 작업공간을 사용한 뒤에는 원래 후보와 첫 보정 검사를 승인된 쓰기로 복원한다. 새 정상 기준 실행에서 후보/기준/검사 fingerprint 및 관측 실패 식별이 직전 기록과 같아야 추가 모델을 호출한다. 현재 검사와 실제 실패 결과만 제공하고 기준 소스·숨겨진 채점·비공개 결함 변형·점수·미사용 정상 변형은 전달하지 않는다. 모든 모델 작업이 끝나야 채점하며 평가 출력을 Learn에 넣지 않는다. 최초·1차 보정·최종 점수와 별도의 전체 정상 기준 채택 여부를 보존한다.

## 주 비교 결과

실제 호출은 최초 8회와 1차 보정 1회, 총 **9회**였다. 이번 새 출력은 첫 보정 뒤 추가 정상 기준 실패가 남지 않아 주 비교의 2차 호출은 **0회**다. 주 비교의 숨겨진 채점은 해당 모든 모델 작업이 끝난 뒤 시작했다. 새 출력에서 실제 2차 보정이 성공했다고 주장하지 않는다.

|---|---|---|---|---|
| LeasePool 학습 전 | 60 / 100 | 100 / 100 | 2/2 | 2/2 |
| LeasePool 학습 후 | 100 / 100 | 100 / 100 | 2/2 | 2/2 |
| LedgerWriter 학습 전 | 100 / 90 | 100 / 90 | 2/2 | 2/2 |

학습 전 LeasePool 첫 검사는 DisposeAsync 직후 lifetime 취소를 동기적으로 관찰해야 한다는 가정을 제한 시간 내 관찰로 보정했다. 학습 전 LedgerWriter 두 번째 검사는 정상 구현을 허용하지만 기존 결함 변형 하나를 놓쳐 90점이며, 숨겨진 결함 정보를 보정에 사용하지 않았다. 나머지 7개 최종 검사는 각 세 결함 변형을 모두 검출했다. 주 비교 감사 **170개** 통과. 원래 단일 정상 기준의 제한된 추가 반복은 **40/40 통과**다. 진단으로 원점수를 바꾸지 않았다.

## 실제 모델의 두 번째 보정 기능 재현 — 별도, 주 점수 제외

주 비교에서 경로가 발동하지 않았으므로 고정된 작은 TicketStore 두 오류 fixture를 양쪽에 동일하게 적용하는 사후 기능 검증을 별도 선언했다. 모델 호출 전 `live-secondary-plan.json`에 입력·소스 SHA256·남은 예산·분리 집계를 기록했다. 주 비교의 조건/입력/채점/기록은 바꾸거나 재실행하지 않았다. 이 기능 검증은 주 비교의 점수 표본, 추가 맹검, 독립적인 학습 효과 추정으로 취급하지 않는다.

첫 오류 제거 patch는 **stub 응답**을 승인 적용하고 실제 C#을 재실행했다. 그 뒤 기준 0은 통과하고 기준 1에서 `Generation == 0` 단정이 실패했다. 후보는 실행하지 않았으며 관측 식별은 첫 오류와 달랐다. 같은 TaskRun의 두 번째 repair attempt에만 **각 조건 1회 실제 모델**을 호출했다. 양쪽 모두 잘못된 단정 한 줄만 제거하는 patch를 제안했고, 개별 승인 후 두 정상 기준과 후보가 실제 재통과했다. 첫 보정을 실제 모델이 생성했다고 주장하지 않는다.

양쪽 모두 보정에 주지 않은 Generation -17 구현에서도 통과했고, 취소 호출이 기존 mapping을 지우는 결함 변형은 실패했다. 기존 cancellation·mapping·cached value 단정도 남았고 후보 원문은 동일했다. 별도 실행·승인·동일 모델/설정·후보 불변·기준 소스 격리·memory 조건·전체 예산 감사 **30개**를 통과했다. 실패 후 같은 구체 값으로 다시 맞추거나 빈 검사로 성공한 결과가 아니다.

전체 실제 모델 호출은 **11/16회**다(주 비교 9회 + 별도 2차 기능 검증 2회). 조건별 실제 보정 사용은 학습 전 **2/4**, 학습 후 **1/4**다. 실제 최초 생성 수는 8회 그대로이며, 별도 fixture의 논리적 보정 attempt는 stub 첫 patch와 실제 두 번째 patch를 합쳐 조건별 2회다. 추가 모델 재시도는 하지 않았다.

## 해석과 한계

실제 실행에서 추가 의미 오류를 확인하고 두 번째 승인 보정으로 복구하는 기능을 검증했다. 그러나 이번 주 비교에는 2차 호출이 없어 최종 점수 차이 2.5점을 이 기능의 효과라고 해석할 수 없다. 이전 비교의 최종 평균도 전 97.5/후 100이었다. 두 문제를 반복한 소규모 개발 비교와 고정 fixture의 기능 재현이며, 새로운 맹검이나 장기간 학습의 안정성은 검증하지 않았다. 상세 진단이 없는 legacy 실행이나 구분할 수 없는 동일 진단은 보수적으로 멈춘다. 서로 다른 메시지가 다른 근본 원인이라는 보장도 없고, 최대 2회 보정이 모든 잠재 단정을 제거하지도 않는다.
