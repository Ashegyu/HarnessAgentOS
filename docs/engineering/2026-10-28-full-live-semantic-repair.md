## 범위와 고정 조건

이전 검증의 첫 patch stub을 대체하여 첫 실패 → 실제 모델의 첫 patch → 승인·실행 → 추가 의미 오류 발견 → 실제 모델의 두 번째 patch → 승인·재실행을 확인했다. 이번 전체 흐름에는 stub 응답이나 미리 만든 patch를 사용하지 않았다. 모델의 원문·provider JSONL·승인된 patch와 실제 C# 실행은 각각 보존했다.

제품 소스는 이전 `03ca709` 실행 manifest와 모두 동일하며 변경하지 않았다. `gpt-5.6-sol / medium`, 300초 timeout/180초 stall 제한, 읽기 전용 모델, 도구/검색 금지, 단일 검사 파일의 작은 patch와 개별 승인 정책을 유지했다. 양쪽은 같은 입력·정상 구현·호출 한도·설정을 사용하고 승인된 학습 3사례의 적용 여부만 다르다. 모델에 정상 구현 원문이나 미사용 정상 변형을 주지 않았고 평가 결과도 학습시키지 않았다.

## 제어된 두 단계 재현

TicketStore의 정상 구현은 취소된 Value를 반환하고 Generation을 0으로 두며, 추가 정상 구현은 취소 반환의 Generation만 long.MinValue로 바꾼다. 이전 기능 검증과 같은 기준 구현이다. 별도 진단의 정상 구현은 Generation -17을 사용한다.

첫 오류는 `CancellationChecks.cs`에서 Get이 취소를 동기 예외로 던진다고 잘못 가정하는 검사다. 두 번째 오류는 `GenerationChecks.cs`의 `Generation == 0` 단정이다. 두 검사를 호출하는 공용 `Program.cs`는 등록 때부터 불변이다. 오류를 파일 둘에 배치하여 기존 1회 1파일 patch 정책으로 두 단계의 실제 실행을 확인했다. 이는 경로를 통제한 기능 검증이며 일반 문제의 성공률이나 맹검 점수에 포함하지 않는다.

| 단계 | 학습 전 | 학습 후 |
|---|---|---|
| 첫 C# 실행 | 정상 기준 0에서 동기 취소 단정 실패 | 동일 |
| 첫 모델 호출 | 실제 응답·pending patch → 개별 승인·적용 | 동일 |
| 첫 보정 후 실행 | 기준 0 통과, 기준 1에서 Generation 단정 실패 | 동일 |
| 실패 구분·상태 | 이전과 다른 관측 실패 식별, 검사 미보호·후보 미실행 | 동일 |
| 두 번째 모델 호출 | 실제 응답·pending patch → 개별 승인·적용 | 동일 |
| 최종 실행 | 기준 0·1과 후보 통과, 품질 passed·검사 보호 | 동일 |

양쪽 첫 모델은 취소된 Ticket.Value를 await하도록 검사만 고쳤다. 첫 수정 당시 Generation 검사 파일은 원문 그대로였다. 두 번째 모델은 다른 파일의 잘못된 Generation 단정만 고쳤으며 첫 수정은 그대로 보존됐다. 후보·공용 진입점도 변경되지 않았다.

두 조건 모두 보정에 쓰지 않은 Generation -17 구현을 통과했다. 기존 mapping을 지우는 결함과 선취소 호출이 빈 mapping을 만드는 결함은 각각 검출했다. 따라서 정상 기준 하나의 값에 다시 맞추거나 기존 유효 검사를 지워서 통과한 결과가 아니다.
