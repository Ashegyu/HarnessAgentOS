# 정상 기준 실행 피드백을 사용하는 검사 보정

## 구현과 판정

실행 소스 `21345ce`에서 정상 기준 실패를 기존 RepairLoop로 연결했다. 프롬프트 지침만 추가한 것이 아니라, 호스트가 실행 원장·승인·현재 품질 gate·계약과 내용 해시를 확인한 다음 실제 실패 로그와 당시 검사 원문을 제공하고, 승인 생성 전에 제안 범위를 검사한다.

- 참조 구현 소스는 보정 입력에 제공하지 않는다. 로그의 유사 문구나 candidate-only 실패를 검사 결함으로 승격하지 않는다.
- 보정 모델은 일반 직접 편집 설정과 관계없이 읽기 전용으로 실행한다. 등록된 검사 경로 한 곳의 `file_patch` 한 개, 추가/삭제 합계 32줄 이하만 제안할 수 있다. 구현 변경·전체 파일 교체·삭제·추가 명령·실행 검사 제안은 거부한다.
- 현재 입력과 gate를 보정 제안 승인 생성 전에 재확인한다. 제안은 pending 승인이고, 사용자 승인 후에도 같은 정상 기준과 후보를 실제 재실행해야 한다. 정상 기준을 통과해 보호된 검사는 이 보정 경로로 변경하지 않는다.
- 별도 TicketStore 회귀에서 계약에 없는 취소된 반환 토큰 Generation 동일성 단정이 실제 C# 정상 기준을 거부하는 것을 재현했다. 작은 검사 patch 후 같은 기준과 후보를 재실행하면 통과하고 나머지 mapping·취소·Value 검사가 남는 것을 확인했다. 모델은 이 제품 회귀에서 stub이며 실제 실행은 .NET이다.

**기능은 작동하지만, 보정 1회로 모든 생성 검사를 복구하거나 Learn의 점수 우위를 확보하지는 못했다.**

## 유지한 조건과 승인받아 추가한 조건

기존 학습 3사례, 평가 2문제, 각 조건 2회, `gpt-5.6-sol / medium`, 초기 코드·요청·시간 예산·도구 금지·60점 구현 + 40점 검사 채점을 유지했다. 기존 컴파일·추출 함수를 그대로 재사용하며 함수 원문 해시를 대조했다. 최초 요청은 양쪽에서 승인된 메모리 외에 동일함을 감사했다.

사용자가 추가로 승인한 조건은 **최대 16회: 최초 생성 8회 + 답안별 보정 최대 1회**다. 양쪽에 같은 호스트 정상 기준 피드백과 보정 제한을 적용했다. 정상 기준이 실패했을 때만 보정하며 candidate-only 실패, 숨겨진 검사, 비공개 결함 변형, 점수, 기준 소스는 모델에 보내지 않았다. 모든 생성·보정이 끝난 뒤 숨겨진 채점을 시작했다. 평가 출력이나 보정 결과를 Learn에 넣지 않았다.

따라서 이전 무피드백 8회 실험과 완전히 동일한 절차라고 주장하지 않는다. 최초 점수와 보정 후 점수를 모두 보존한다.

## 실제 결과

실제 호출은 최초 8회 + 보정 4회 = **12회**였고, 추가 호출 없이 종료했다.

| 문제 / 조건 | 최초 1 / 2회 | 보정 후 1 / 2회 |
|---|---|---|
| LeasePool 학습 전 | 60 / 60 | 100 / 100 |
| LeasePool 학습 후 | 60 / 100 | 60 / 100 |
| LedgerWriter 학습 전 | 100 / 60 | 100 / 100 |
| LedgerWriter 학습 후 | 100 / 100 | 100 / 100 |
| 전체 평균 | 학습 전 70 / 학습 후 90 | 학습 전 100 / 학습 후 90 |

8개 구현 모두 숨겨진 구현 검사 60점을 받았다. 보정 4개 중 3개는 같은 정상 기준과 후보에서 재통과했다. 학습 전 조건에서는 즉시 취소 단정 2개와 `Sequence(null!)`의 잘못된 null 인자 전달 1개가 작은 patch로 복구됐다.

학습 후 LeasePool 첫 검사는 즉시 취소 단정을 비동기 관측으로 바꿨지만, `TimeSpan Timeout` 필드가 있는 코드에서 `Timeout.InfiniteTimeSpan`을 추가하여 CS1061로 컴파일에 실패했다. 실제 정상 기준 재실행이 거부했고 후보 실행은 시작하지 않았다. 보정 1회 제한을 늘리거나 원래 60점을 통과로 바꾸지 않았다. 최종 평균은 학습 전 100, 학습 후 90이므로 **이번 결과에서 Learn의 최종 점수 우위는 없다.**

## 별도 진단과 검증

- 새 보정·Agent·RepairLoop 회귀 77개 통과, 실제 C# Generation 실패→검사 보정→같은 기준/후보 재실행 포함. 새 context 경로 line coverage 100%, branch 82.05%.
- 기존 Runner·품질 실행·검사 보호 경계 65개 통과. 이 범위에서 기존 opt-in C# 사례 5개는 실행하지 않았다.
- `npm run check`, `npm run build` 통과. 빌드에 기존 Zod annotation 경고가 있었으며 오류는 없었다.
- 조건·격리·소스 고정 감사 59개 통과. 감사 도구가 원래 공개된 초기 코드(결함 변형 0과 동일)를 비공개 피드백으로 오인한 4개 항목을 정정했다. 실제 비공개 변형·숨겨진 검사·기준 소스는 입력에 없었다. 최초 감사도 보존하고 모델 호출·점수·재실행 결과는 변경하지 않았다.
- 컴파일된 최종 검사 7개를 같은 정상 기준에서 각 5회, 총 35회 추가 실행해 모두 통과했다. 컴파일 실패한 검사 1개는 제외했다. 원점수는 바꾸지 않았다.
- Generation 추가 정상 구현 진단: 취소된 반환 토큰의 Generation만 0 대신 `long.MinValue`로 바꾼 LeasePool 기준이 기존 숨겨진 구현 검사 전체를 통과하는지 먼저 확인했다. 컴파일된 LeasePool 최종 검사 3개는 이 정상 구현에서도 통과했다. 나머지 1개는 앞선 컴파일 오류로 검사하지 못했다. 이 진단은 모델 피드백이나 채점에 사용하지 않았다.

새 C# 생성 품질의 일반적 안정성, 장기간 사용에 따른 개선, 새로운 맹검 문제, GUI 클릭, 모델 가중치 학습은 검증하지 않았다. 단일 정상 기준 통과는 계약 전체의 증명이 아니고 작은 patch 제한도 의미적 coverage 보존의 증명은 아니다. 기준 구현은 사용자 신뢰를 전제로 하며 보정 한도가 끝나면 실패를 남기고 중단한다.
