# 다중 정상 구현을 실행하는 회귀 검사 채택·보정

## 원인과 변경

기존에는 정상 기준 구현 하나에서 검사가 통과하면 즉시 검사 원문을 보호했다. 취소된 반환 토큰의 Generation을 0으로 정한 기준에서는 계약에 없는 `Generation == 0`도 통과했다. 같은 계약을 지키되 그 값을 `long.MinValue`로 반환하는 구현을 등록해 실행해야 이 오판을 드러낼 수 있었다. 반복 실행만으로는 이를 해결하지 못한다.

`additionalReferenceDirs`로 추가 정상 구현을 최대 3개 등록한다. 사용자가 신뢰한 기준 집합·공용 계약은 SQLite의 기존 definition_json에 동결한다. 새 JSON 파일을 canonical state로 사용하지 않는다. 구 데이터의 단일 기준 fingerprint는 유지하고, 추가 기준이 있는 계약의 fingerprint와 승인 입력은 전체 기준을 포함한다. 중복 경로/원문, 부적절한 경로, 합계 8 MiB 초과를 거부한다. 별도 DB migration은 없다.

같은 검사로 등록 기준을 순서대로 실행하고 전부 통과해야 검사 보호와 후보 실행을 허용한다. 기준 집합은 합계 120초 예산을 공유한다. 나중 기준의 실패·취소·입력 변경은 앞선 성공을 채택으로 승격하지 않는다. 호스트 증거에 기준 수와 실제 실행한 순서별 종료 코드를 기록하고, 그룹 불일치/위조/오래된 입력은 보정 근거로 쓰지 않는다. 이미 보호한 검사는 자동 해제하지 않는다. 기존 계약에 기준을 나중에 덧붙이는 API도 추가하지 않았다.

실패한 검사만 현재 실행 로그·그룹 결과·검사 원문으로 보정한다. 기준 소스는 모델에게 주지 않는다. 기존 읽기 전용 모델, 최대 32개 변경 행의 단일 검사 patch, pending 승인, 후보 원문 보존, 적용 후 같은 전체 집합 재실행을 유지한다. 후보만 실패한 경우에는 이 검사 보정 경로를 사용하지 않는다. UI에는 선택적인 추가 기준 경로와 기준 수·전체 통과 대기를 표시한다. GUI 클릭 검증은 수행하지 않았다.

## 비교 조건

모델 실행 소스는 **435fbf6**으로 고정했다. 기존 학습 3사례, LeasePool/LedgerWriter 두 문제, 각 조건 두 번, 최초 요청·코드·모델 `gpt-5.6-sol / medium`·도구 금지·시간 제한·숨겨진 검사·결함 변형 3개·구현 60점 + 검사 40점 배점을 유지했다. 양쪽 모두 새 기준 묶음을 적용했고, 예산도 최초 8회·총 최대 16회·조건별 보정 최대 4회로 같다. 기존 최초 보정 1회와 그 뒤 실제 검사 컴파일 오류에만 허용하는 재보정 정책도 유지했다.

LeasePool은 Generation만 0 → long.MinValue로 바꾼 정상 기준, LedgerWriter는 분리된 스냅샷의 열거 순서만 달리한 정상 기준을 추가했다. 보정에 쓰지 않은 변형은 각각 Generation -17과 반대 열거 순서다. 네 변형 모두 모델 호출 전에 원래 숨겨진 검사 전체 통과를 확인했다. **주 점수는 기존 단일 기준과 기존 결함 변형으로 그대로 계산**하고, 다중 기준 채택 및 미사용 정상 변형은 별도 지표로 기록했다.

실제 호출은 **13회: 최초 8회 + 1차 보정 5회**였다. 컴파일 재보정은 0회다. 숨겨진 채점은 모든 호출이 끝난 후 시작했다. 평가 출력을 Learn에 넣거나 결과에 맞춰 지침·코드를 바꾸지 않았다. 동결 소스·동일 학습 원문·예산·후보 불변·승인된 보호 원문·도구 금지·비공개 소스 격리 등 감사 **153개**를 통과했다.

학습 후 LeasePool 두 검사는 취소된 반환 토큰이 현재 Generation과 같아야 한다는 비계약적 단정을 제거했다. 한 검사는 별도의 정상 조회로 실제 캐시가 보존됐는지 검사하여 유효한 coverage도 유지했다. 정상 기준 두 개와 미사용 -17 구현에서 모두 통과했고 기존 세 결함 변형을 모두 검출했다. 학습 전 LedgerWriter의 CS8752는 실제 빌드 진단 후 타입을 명시한 patch로 복구됐지만 결함 변형 하나는 놓쳐 90점을 받았다.

**남은 실패도 보존했다.** 학습 전 LeasePool 두 번째 검사는 최초 기준에서 DisposeAsync 직후 취소를 관찰해야 한다는 별도 가정 때문에 먼저 실패했다. 첫 보정은 그 가정만 고쳤다. 그 뒤 두 번째 정상 기준이 실행되자 남아 있던 `Equal(0L, rejected.Generation)`이 실패했다. 기존 배점으로는 여전히 100점이나 새 채택 경로는 이를 보호하거나 후보를 실행하지 않았다. 미사용 정상 구현도 `Expected '0', actual '-17'`로 같은 문제를 확인했다. 정상 의미 오류에 대한 두 번째 보정은 동결 프로토콜의 허용 범위 밖이므로, 남은 전역 호출 수를 이유로 추가 실행하지 않았다. 이번 실제 모델 비교에서 **0 단정을 끝까지 자동 제거한 성공 사례**라고 보고하지 않는다. 실제 C# 기능 회귀에서는 이 직접 실패를 받은 작은 승인 patch로 복구되는 것을 별도로 확인했다.

최종 검사 각각을 원래 단일 기준에서 5회씩, 총 **40회** 더 실행하여 모두 통과했다. 그러나 위 0 단정은 다른 정상 구현에서 실패했다. 이 진단은 동일 구현 반복의 한계를 보여주며 원점수를 변경하지 않는다.
