§ 02 · CODEX CLI 의 NEW · 알아야 할 변화

Codex CLI는 더 이상 단순한 CLI가 아니다.

2026년 초까지의 Codex CLI는 Claude Code와 거의 같은 primitives를 갖췄다. AGENTS.md, Hooks, MCP, Skills, Subagents, Plugins, Slash commands — 둘 사이의 격차가 빠르게 줄었다. 이는 4개 프로젝트의 cross-harness 지원이 기술적으로 가능해진 이유이기도 하다.

[ PRIMITIVE 01 ]
📄 AGENTS.md
vs CLAUDE.md

프로젝트의 컨벤션, 빌드/테스트 명령, 도메인 어휘를 담은 brief. 글로벌(~/.codex/AGENTS.md) + 프로젝트 루트(./AGENTS.md) 계층 지원.

[ PRIMITIVE 02 ]
🔧 MCP Servers
vs Claude Code MCP

~/.codex/config.toml의 [mcp_servers.<name>] 섹션에 등록. STDIO/HTTP 모두 지원. Codex 자체를 MCP server로 expose 가능.

[ PRIMITIVE 03 ]
⚡ Hooks
vs Claude Code Hooks

Codex는 자체 Hooks 시스템 보유. Claude Code의 hook event 수(8개)에 비해 다양성은 적음. ECC의 cross-harness adapter로 둘 다 지원 가능.

[ PRIMITIVE 04 ]
📚 Skills
SAME as Claude

Codex CLI도 SKILL.md 기반 skills 지원. agentskills.io 표준 호환. Hermes/ECC/Ruflo의 skills를 그대로 사용 가능.

[ PRIMITIVE 05 ]
👥 Subagents
vs delegate_tool

Codex는 [agents] 섹션에서 role-configured subagents 정의. 명시적으로 요청 시에만 spawn. 토큰 사용량 high.

[ PRIMITIVE 06 ]
🧩 Plugins
vs Claude Plugins

Codex CLI 자체 plugin marketplace 있음. codex plugin CLI로 add/upgrade/remove. ECC는 Codex용 별도 plugin manifest 제공.

[ PRIMITIVE 07 ]
/ Slash Commands
SAME as Claude

/init, /model, /plan, /personality 등. Type /로 popup. Tab으로 queue.

[ PRIMITIVE 08 ]
🛡️ Sandbox + Approval
vs allowed/confirm

--sandbox workspace-write + --ask-for-approval on-request. 격리된 macOS/Linux/Windows sandbox.

[ PRIMITIVE 09 ]
🦀 Rust + Open Source
vs Claude (Node.js)

Codex CLI는 Rust로 작성, open source (MIT). 빠른 startup. Kim님의 .NET 환경과는 별개 프로세스로 동작.

⚡ Skillify에 미치는 함의

Claude Code와 Codex CLI는 더 이상 별개의 세계가 아니다. 두 harness가 같은 primitives를 갖췄으므로, Skillify를 처음부터 cross-harness 디자인으로 설계하면 동일 코어를 두 harness 모두에서 활용 가능하다. Reference 모델은 ECC — 4개 중 유일하게 Claude/Codex/Cursor/OpenCode/Gemini/Antigravity 모두 지원하는 패턴을 검증했다.

03.1 · ARCHITECTURE

계층적 swarm으로 구성된 오케스트레이션

Ruflo의 핵심은 "단일 에이전트가 아닌 swarm"이라는 점이다. 사용자가 Claude Code에 명령을 내리면, Ruflo의 Router가 작업을 분석해서 적절한 Swarm을 구성하고, 그 swarm 안에서 여러 Agent가 협력해 작업을 수행한다. 모든 결과는 Memory에 저장되고 Learning Loop를 통해 다음 작업에 반영된다.

03.2 · KEY FEATURES

[ 01 ]
🐝 Swarm Topology

[ 02 ]
🧠 SONA + ReasoningBank

04.1 · ARCHITECTURE

3-Layer 플랫폼 모델

명확하게 3계층 분리: SDK(에이전트 빌드) / Runtime(FastAPI service) / Control Plane(SaaS UI). Control Plane만 closed-source, 나머지는 완전 오픈소스. 철학적으로 LangServe + LangSmith의 LangChain 스타일에 가깝다.

04.2 · DEVELOPER EXPERIENCE

30줄로 production service

from agno.agent import Agent
from agno.db.sqlite import SqliteDb
from agno.os import AgentOS
from agno.tools.workspace import Workspace

workbench = Agent(
    name="Workbench",
    model="openai:gpt-5.4",
    tools=[Workspace(".",
        allowed=["read", "list", "search"],
        confirm=["write", "edit", "delete", "shell"],
    )],
    enable_agentic_memory=True,
)

agent_os = AgentOS(agents=[workbench], db=SqliteDb(...))
app = agent_os.get_app()

# $ fastapi dev workbench.py
# → http://localhost:8000 (with /docs OpenAPI)
⚡ 주목할 점

allowed/confirm 분리. read/list/search는 자유, write/edit/delete/shell은 human approval. 이 패턴이 Skillify의 "LLM-judgment vs deterministic-code" 분리 철학과 완전히 같다. 위험한 액션을 자동화하지 않고 명시적 confirm을 받는 게이트 메커니즘.

06.1 · ARCHITECTURE

Hooks-first 결정적 관찰 시스템

ECC의 핵심 통찰: "Skills는 확률적이다 (~50-80%의 확률로 발동). Hooks는 결정적이다 (100% 발동)". 이 한 줄이 ECC v2 전체 아키텍처를 설명한다. Skills로 관찰하던 v1을 버리고, PreToolUse/PostToolUse hooks를 통한 100% 결정적 관찰로 전환했다. 이게 정확히 Skillify의 "LLM-judgment vs deterministic-code 엄격 분리" 철학이다.

06.2 · CONTINUOUS LEARNING V2 (★ MOST CRITICAL FOR SKILLIFY)

Instinct → Skill 진화 파이프라인

ECC의 가장 중요한 부분이자 Skillify의 직접 reference. Hermes가 한 번에 "skill"을 만든다면, ECC는 더 세분화된 접근을 한다: 먼저 작은 atomic "instinct"를 만들고, 충분히 신뢰도가 쌓이면 cluster해서 skill로 진화시킨다. 이는 Skillify의 "실패 → reusable skill artifact" 컨셉을 더 세밀한 단위로 분해한 형태이다.

Instinct의 자료구조 (YAML)

# instincts/personal/prefer-functional-style.yaml
---
id: prefer-functional-style
trigger: "when writing new functions"
confidence: 0.7 # 0.3 → 0.9 진화
domain: "code-style" # code-style, testing, git, debugging...
source: "session-observation"
scope: project # or 'global'
project_id: "a1b2c3d4e5f6" # git remote hash
project_name: "my-react-app"
---

# Prefer Functional Style

## Action
Use functional patterns over classes when appropriate.

## Evidence
- Observed 5 instances of functional pattern preference
- User corrected class-based approach to functional on 2025-01-15

Confidence Scoring (0.3 → 0.9)

0.3  # Tentative · 제안만 함, 강제 안 함
0.5  # Moderate · 관련 시 적용
0.7  # Strong · 자동 승인되어 적용
0.9  # Near-certain · 핵심 행동 (always-on)

Confidence 증가 조건:
  - 패턴이 반복 관찰됨
  - 사용자가 제안된 행동을 정정하지 않음
  - 다른 소스의 비슷한 instincts가 동의

Confidence 감소 조건:
  - 사용자가 명시적으로 행동 정정
  - 오랜 기간 패턴이 관찰되지 않음
  - 모순되는 증거 출현

v1 vs v2 비교 — 왜 hooks로 갈아탔는가

                v1                          v2
Observation     Stop hook (session end)     PreToolUse/PostToolUse hooks
Reliability     ~50-80%                     100% reliable
Analysis        Main context (오염)         Background agent (Haiku, 격리)
Granularity     Full skills (큼)            Atomic instincts (작음)
Confidence      None                        0.3-0.9 weighted
Evolution       Direct to skill             Instincts → cluster → skill/command/agent
Sharing         None                        Export / Import

  • Multi-tenant / RBAC 없음: 개인용/팀용으로만 설계.

06.7 · APPLICATION TO SKILLIFY (★ HIGHEST PRIORITY)

Skillify에 어떻게 적용할까

ECC는 차용이 아닌 직접 포팅 reference로 사용해야 한다. Skillify의 핵심 컨셉이 ECC v2와 동일하므로, ECC의 검증된 메커니즘들을 .NET 10에 맞춰 그대로 옮기는 게 최단 경로. 다음 7가지를 우선순위 순으로 적용한다:

★ 01
최우선 · IMMEDIATE
Instinct 모델 도입 (Skill 이전 단계의 atomic 단위)

현재 Skillify가 "실패 → skill" 단일 단계라면, ECC처럼 "실패 → instinct → cluster → skill" 2단계로 분해. 각 instinct는 작고 atomic, confidence (0.3 → 0.9), domain 태그를 가진다.

.NET 구현:
• Skillify.Core.Instincts.Instinct record (immutable, source-generated JSON)
• ReadOnlySpan<char>으로 confidence 업데이트 시 allocation 없음
• FrozenDictionary<DomainTag, ImmutableArray<Instinct>>로 fast lookup
• Kim님의 zero-allocation 패턴과 자연스럽게 결합.

★ 02
최우선 · IMMEDIATE
Project Scoping + Promotion 메커니즘

ECC의 v2.1 project scoping 그대로 채택. git remote hash로 portable project ID 생성.

.NET 구현:
• SQLite per-project로 instincts/skills 격리 (Kim님 이미 SQLite 사용 중)
• ProjectIdentity.From(gitRemoteUrl) static method로 hash 생성
• SkillRegistry.Global + SkillRegistry.Project(id) 이중 lookup
• /promote command for project → global when confidence ≥ 0.8 across N projects

★ 03
최우선 · IMMEDIATE
Confidence Scoring 메커니즘

단순 카운터로 confidence를 계산하지 말고, ECC처럼 차등 가중치:

증가: 반복 관찰 (+0.05), 사용자 미정정 (+0.02), 비슷한 instinct 동의 (+0.03)
감소: 사용자 정정 (−0.15), 오랜 미관찰 (decay −0.01/week), 모순 증거 (−0.10)

이렇게 하면 단순 빈도가 아닌 "의미 있는 학습"이 측정된다. Bayes update 변형으로도 구현 가능.

★ 04
우선 · HIGH
Background Observer 격리 패턴 + 5-Layer Guard

ECC의 "메인 컨텍스트를 오염시키지 않는 background Haiku agent" 그대로 적용.

.NET 구현:
• BackgroundService (ASP.NET Core) 또는 별도 console worker로 격리
• Channel<T>로 observation 큐, throttled signaling
• Anthropic Claude Managed Agents를 background analyzer로 활용 (Kim님 탐색 중)
• 5-Layer self-observation guard도 반드시 포팅 — hook recursion은 실제로 흔한 함정.

★ 05
중요 · MEDIUM
Evolution Triggers (/evolve, /promote)

ECC의 /evolve가 instincts를 cluster해서 skill을 만드는 메커니즘은 Skillify의 핵심 가치.

조건: 같은 domain의 instincts가 N개 이상 + 평균 confidence ≥ 0.7
SkillEvolver.AnalyzeClusters()가 domain별로 instinct 그룹화 → EvolutionCandidate 생성 → 사용자 승인 후 SkillRegistry.Save(skill)

★ 06
고려 · CONSIDERATION
AgentShield 보안 스캐닝 통합

외부 skill/instinct import 시 보안 검증 필수. ECC의 AgentShield (1,282 tests, 102 rules)는 14 secret patterns, permission auditing, hook injection analysis 수행.

Kim님의 ECDIS 환경(maritime safety-critical) 특성상 보안 스캐닝은 must-have. ECC의 trust level (builtin/official/trusted/community) 4단계도 그대로 채택.

★ 07
장기 · LONG-TERM
ECC 2.0 Rust Control Plane 모니터링

ECC 2.0 alpha의 ecc2/는 Rust로 작성된 control plane. dashboard, start, sessions 등의 명령 노출.

Kim님의 .NET 10 환경과 직접 통합되진 않지만, "performance-first compiled language로 control plane을 만든다"는 방향성이 Skillify와 일치. ECC 2.0이 더 성숙해지면 gRPC IPC로 통합 가능.

§ 07 · CODEX CLI 적용 — 한눈에 비교

네 프로젝트의 Codex 통합 방식.

Codex CLI 지원 등급별로 분류한 요약. 4개 프로젝트가 매우 다른 통합 방식을 채택한다.

CODEX TIER S · FIRST-CLASS NATIVE
ECC ★
Codex CLI 안에 직접 통합 (plugin/skills를 Codex가 직접 로드)

4개 중 유일하게 진정한 cross-harness. 처음부터 cross-harness로 설계되었고, 모든 48 agents/182 skills가 Codex에서 동일하게 작동.

git clone .../everything-claude-code
cd everything-claude-code
npm install && bash scripts/sync-ecc-to-codex.sh
# → ~/.codex/config.toml 자동 안전 병합

Skillify 차용 가치: ★ 최고 — 청사진. Per-harness 디렉토리, safe-merge 스크립트, Node.js cross-platform hooks 패턴 그대로.

CODEX TIER A · DUAL ORCHESTRATION
Ruflo
Claude 워커 + Codex 워커 동시 spawn, swarm에서 협력

가장 야심찬 접근. @claude-flow/codex 별도 패키지, claude-flow-codex dual CLI로 두 harness를 동시 제어.

npx ruflo@alpha init --codex     # Codex 모드
npx ruflo@alpha init --dual      # Claude + Codex 동시

npx claude-flow-codex dual run \
  --worker "claude:architect:..." \
  --worker "codex:coder:..."

Skillify 차용 가치: 중간 — over-engineered하지만 --worker "harness:role:task" declarative 명세 패턴은 즉시 차용 가능.

CODEX TIER A · DELEGATION
Hermes
Codex를 sub-agent로 호출 (Hermes가 Codex CLI를 spawn)

두 가지 방향: ⓐ Codex GPT-5.5를 Hermes provider로 사용, ⓑ Hermes 안에서 Codex CLI를 sub-agent로 호출. ⓑ가 핵심.

# Codex를 Hermes provider로 (GPT-5.5 OAuth)
hermes auth add openai-codex

# Codex CLI를 sub-agent로 호출
terminal(command="codex --yolo exec '...'",
  workdir="/tmp/issue-78",
  background=True, pty=True)

Skillify 차용 가치: 중간-높음. CEO→Executor 패턴과 완벽 일치. Git worktree + parallel Codex spawn 패턴이 즉시 .NET에서 활용 가능.

CODEX TIER C · MODEL ONLY
Agno
Codex CLI harness와는 무관 (모델만 사용 가능)

Agno는 backend service, Codex CLI는 frontend tool이라 abstraction layer가 다르다. 간접 통합은 MCP server로 expose해서 가능.

# Agno → Codex CLI 우회 경로
# 1. Agno를 MCP server로 expose
# 2. Codex의 ~/.codex/config.toml에 등록
[mcp_servers.agno]
command = "npx"
args = ["-y", "agno-mcp-server"]

Skillify 차용 가치: 낮음. Codex CLI 측면에서는 거의 무관. Agno의 가치는 Phase 3 SaaS화에서.

13.3 · ZERO-COPY · 저할당 NETWORK 처리 6대 포인트

Kim님의 zero-allocation 패턴 적용

[ 01 ]
System.Text.Json source generator

Reflection 기반 serializer 대신 compile-time metadata 사용. JsonSerializerContext + [JsonSerializable]. AOT 친화적.

[ 02 ]
Utf8JsonReader

Hot path에서 DOM 파싱(JsonDocument) 남발 금지. Streaming parse. ref struct 형태로 stack-only, allocation 없음.

[ 03 ]
PipeReader / System.IO.Pipelines

SSE/streaming 응답을 chunk 단위로 읽고, line/event boundary만 잘라 처리. backpressure 자연스럽게.

[ 04 ]
Channel<T> (System.Threading.Channels)

Agent event를 bounded channel로 흘려 backpressure 명확히. producer/consumer 분리. UnboundedChannelOptions 절대 피하기.

[ 05 ]
ArrayPool<byte> / MemoryPool<byte>

대형 tool result, file diff, trace payload 처리 시 버퍼 재사용. ArrayPool.Shared.Rent() + try/finally로 안전 반환.

[ 06 ]
ValueTask + 프로세스 격리

동기 완료 잦은 adapter path에서 task allocation 감소. AI agent의 memory leak/GC를 C# 앱 성능 경로에서 분리.

## Project identity
- This is a C#/.NET 10 project.
- Prioritize correctness, deterministic behavior, allocation minimization, maintainability.
- Do not introduce new production dependencies without explicit justification.

## Build and verification
- After modifying C# files, run:
  - dotnet build -c Release
  - dotnet test -c Release
- For performance-sensitive changes, add or update BenchmarkDotNet benchmarks.
- For public APIs, update XML docs and usage examples.

## C# performance policy
- Prefer Span<T>, ReadOnlySpan<T>, Memory<T>, ReadOnlyMemory<T> where ownership is clear.
- Prefer ArrayPool<T> or ObjectPool<T> only when lifetime and clearing rules are explicit.
- Avoid LINQ in hot paths.
- Avoid hidden allocations from closures, async state machines, boxing,
  string interpolation, and params arrays in hot paths.
- Prefer System.Text.Json source generation for stable DTOs.
- Use Utf8JsonReader/Utf8JsonWriter for zero-copy JSON parsing in high-throughput paths.
- Use ValueTask only when measurably beneficial.
- Do not use unsafe code unless there is a benchmark and a clear safety boundary.

## Review behavior
- Before editing, state the plan and risk.
- Make minimal diffs.

# Dotnet Performance Review

Use this skill when reviewing C# code for performance-sensitive paths.

## Workflow

16.1 · CODEX 적용 전용 리스크

Codex CLI 통합 시 7가지 함정

[ 01 ]
중복 instructions

AGENTS.md + skill + prompt + hook additional context가 같은 규칙을 반복하면 모델이 혼란. Skillify는 single source of truth 유지.

[ 02 ]
Hook 과신

Hook은 guardrail이며 sandbox를 대체하지 않음. PreToolUse는 Bash/apply_patch만 intercept. sandbox_mode + approval_policy와 함께 사용.

[ 03 ]
Network/tool risk

MCP와 web search는 prompt injection 경로. network_access = false를 기본으로. Codex의 sandbox_workspace_write에서 명시.

[ 04 ]
Secret leakage

shell_environment_policy로 TOKEN/SECRET/KEY/PASSWORD 계열을 차단. *_TOKEN, *_SECRET glob 패턴 활용.

[ 05 ]
Skill bloat

ECC 전체 skills (182개)를 모두 넣지 말고 프로젝트별 curated subset 유지. 5~15개부터 시작. fallback_for_toolsets로 조건부 활성화.

[ 06 ]
C# host 권한

Codex process를 같은 권한으로 실행하면 host 앱의 모든 권한 상속. 별도 계정/worktree/container 권장.

[ 07 ]
CI 자동 수정

초기에 자동 commit/push 금지. Report 생성과 patch proposal까지만 허용. 사람 review 후 merge.
