1. 결론 요약

가장 실용적인 결론: 제품에 직접 넣을 “에이전트 백엔드”는 여전히 Agno가 가장 적합합니다. 개발 워크플로우 자동화는 Ruflo와 Everything Claude Code(ECC)가 강하고, 개인/운영 자동화와 장기 실행 assistant는 Hermes-Agent가 강합니다. ECC는 Ruflo와 같은 “Claude Code 강화” 계열이지만, 더 넓은 harness/IDE/Codex/Cursor/OpenCode 적응 레이어와 hook/rule/skill 공급망 관리 성격이 강합니다.

Ruflo

핵심 정체성: Claude Code를 중심으로 다수의 특화 에이전트, swarm, MCP 도구, 메모리, hook, plugin을 붙이는 개발 자동화 오케스트레이터입니다.

적합한 용도: 대형 코드베이스 분석, 구현 계획 분해, 병렬 에이전트 작업, Claude Code 기반 자동화.

주의: 패키지/브랜치/문서상의 이름과 수치가 일부 혼재되어 있습니다. 도입 전 설치 버전과 실제 도구 수를 반드시 검증해야 합니다.

Agno

핵심 정체성: Agent, Team, Workflow를 만들고 AgentOS Runtime/API/Control Plane으로 운영하는 프로덕션 지향 SDK입니다.

적합한 용도: SaaS/업무 시스템에 agent API, session, memory, DB, RBAC, HITL, tracing, scheduler를 붙이는 경우.

주의: Python 생태계와 FastAPI/DB 운영 전제가 강합니다. C# 제품에는 out-of-process agent service로 붙이는 구조가 적합합니다.

Hermes-Agent

핵심 정체성: TUI, messaging gateway, cron, skills, curated memory, terminal/browser tools를 갖춘 자기개선형 장기 실행 에이전트입니다.

적합한 용도: 개인 AI 비서, Telegram/Discord 기반 운영 봇, 서버/샌드박스에서 실행되는 개발·리서치 자동화.

주의: 도구 실행면이 넓고 자율성이 강합니다. 제품에 붙일 때는 권한·샌드박스·승인 정책을 강하게 제한해야 합니다.

Everything Claude Code

핵심 정체성: Claude Code, Codex, Cursor, OpenCode 등 agent harness 전반에 skills, agents, hooks, rules, MCP 설정, installer, security scanner를 제공하는 성능 최적화/운영 패키지입니다.

적합한 용도: 개발팀 표준 agent harness, 코딩 규칙 자동 적용, hook 기반 품질 게이트, skill/rule 재사용, 보안 스캔, multi-harness 설정 배포.

주의: 제품 runtime SDK가 아니라 “개발 환경 운영체제”에 가깝습니다. C# 앱에 직접 임베딩하기보다는 개발팀/CI/agent workspace 계층에 적용해야 합니다.

5. Ruflo 상세 분석

5.1 소스의 성격

Ruflo는 일반적인 “agent framework SDK”라기보다 Claude Code 위에 얹는 multi-agent orchestration layer에 가깝습니다. 문서상으로는 specialized agents, swarm, self-learning memory, model routing, MCP server, hooks, plugins, Web UI, federation까지 포함하는 큰 플랫폼입니다.

저장소 구조는 단일 작은 라이브러리 형태가 아니라 v3, plugins, docs, mcp, agents, goal_ui, @claude-flow/* 패키지 구조가 섞여 있습니다. 실제 패키지명도 일부 문서/메타데이터에서 claude-flow와 Ruflo가 혼재합니다. 도입 시 README보다 설치되는 npm package, CLI command, 실제 MCP tool list를 기준으로 검증해야 합니다.

5.2 동작 방식

  1. 초기화: 프로젝트에 Ruflo 설정, Claude Code hooks, MCP server, plugin/agent 정의를 설치합니다.
  2. 입력 수신: 사용자가 Claude Code slash command 또는 일반 프롬프트를 입력합니다.
  3. 라우팅: hook/router가 작업 유형을 판단하고, 필요한 memory search, model selection, swarm mode를 결정합니다.
  4. Swarm 구성: architect, coder, reviewer, tester, security, documentation 등 역할별 agent가 생성되거나 선택됩니다.
  5. 도구 호출: MCP tool을 통해 파일, 코드, memory, planner, neural module, 외부 API 등을 호출합니다.
  6. 결과 통합: agent들의 산출물을 합치고, 코드 변경/리포트/plan/검증 결과를 생성합니다.
  7. 학습 루프: memory store, reasoning bank, neural train, token/model router 업데이트 등으로 다음 작업에 반영합니다.
Ruflo 작업 흐름 예시 /plan "3D airplane simulator physics engine 설계" └─ Router: task=architecture + performance-critical C# ├─ memory_search: 과거 설계/코딩 룰 검색 ├─ swarm_init: hierarchical 또는 mesh swarm 구성 │ ├─ architecture-agent │ ├─ performance-agent │ ├─ graphics-agent │ ├─ physics-agent │ └─ security/review-agent ├─ 각 agent가 병렬 분석 ├─ reviewer가 충돌/누락 검토 ├─ plan/checklist 산출 └─ memory_store: 좋은 설계 패턴과 오류를 저장

5.3 주요 기능

Swarm / Hive Mind

여러 agent를 역할별로 분리해 하나의 작업을 병렬/계층적으로 처리합니다. 구현 계획, 코드 작성, 테스트, 리뷰, 문서화처럼 서로 다른 사고 방식이 필요한 작업에 적합합니다.

MCP Tool Layer

Claude Code 또는 다른 MCP client가 Ruflo 기능을 도구로 호출할 수 있습니다. memory, swarm, neural, federation, file/code 작업 등이 tool surface가 됩니다.

Memory / Learning

HNSW vector search, AgentDB, knowledge graph, ReasoningBank 등으로 설명된 memory layer를 통해 과거 작업과 의사결정을 재사용하는 구조입니다.

Model Router

작업 유형과 성능/비용/성공률에 따라 모델을 선택하는 routing 계층을 둡니다. 문서에는 Thompson sampling 기반 selector도 언급됩니다.

Plugin Catalog

core, swarm, memory, ADR, DDD, SPARC, security audit, testgen, browser 등 다수의 Claude Code plugin 카탈로그가 있습니다.

Federation

복수 설치 간 agent peering, Ed25519 identity, trust ladder, signed envelopes, budget/circuit breaker, PII pipeline을 문서화하고 있습니다.

5.4 장점

  • Claude Code 친화성: Claude Code를 주 개발 도구로 쓴다면 hook, slash command, plugin, MCP가 바로 workflow에 들어옵니다.
  • 개발 작업 분해에 특화: architecture, coding, testing, review, documentation을 여러 agent로 나누는 방식이 코드베이스 작업에 잘 맞습니다.
  • 도구 표면이 큼: memory, swarm, federation, planner 등 다양한 MCP 도구가 있어 실험 범위가 넓습니다.
  • 장기적 학습 방향: 작업 히스토리와 memory를 바탕으로 반복 개발 효율을 높이는 방향성이 명확합니다.

5.5 단점과 리스크

  • 브랜드/패키지명 혼재: 저장소명은 Ruflo지만 패키지/문서에는 claude-flow 계열이 함께 나타납니다. 자동화 스크립트 작성 시 혼동될 수 있습니다.
  • 기능 수치 불일치 가능성: README, status 문서, package metadata가 말하는 agent/tool/version 수치가 다를 수 있습니다.
  • 제품 임베딩보다는 개발환경 중심: C# 런타임 안에 라이브러리처럼 넣기보다는 외부 orchestrator로 쓰는 편이 현실적입니다.
  • 보안면이 넓음: 파일/쉘/코드 변경/메모리/외부 provider를 다루므로 강한 sandbox와 approval policy가 필요합니다.

6. Agno 상세 분석

6.1 소스의 성격

Agno는 네 저장소 중 가장 제품 백엔드로 바로 전환하기 쉬운 Agent SDK입니다. Agent, Team, Workflow를 코드로 구성하고, AgentOS를 통해 API, session, memory, storage, tracing, control plane, scheduler, approval flow를 운영하는 방향입니다.

C# 개발자 관점에서 Agno의 장점은 “언어가 Python이라서 아쉽다”가 아니라 외부 agent microservice로 분리하기 좋다는 점입니다. C# 앱은 인증/과금/UI/도메인 로직을 담당하고, Agno는 Agent API를 담당하게 하면 경계가 명확합니다.

6.2 동작 방식

  1. Agent 정의: model, instructions, tools, memory/storage, knowledge base, expected output 등을 Python 코드로 선언합니다.
  2. Runtime 실행: AgentOS runtime이 FastAPI 형태로 올라가고 client는 HTTP/SSE/WebSocket으로 agent run을 요청합니다.
  3. Tool orchestration: agent가 필요한 toolkits/custom tools/MCP tools를 선택하고 실행합니다.
  4. HITL/승인: 위험한 tool call은 confirmation이나 user approval 이벤트를 통해 멈췄다가 재개할 수 있습니다.
  5. Storage/Memory: session, user, run, memory, knowledge, trace가 DB/vector store에 남습니다.
  6. 운영 관찰: Control Plane/trace/audit를 통해 어떤 요청에서 어떤 도구가 호출됐는지 확인합니다.

Agent / Team / Workflow

DB-backed session/memory/knowledge 구조가 명확합니다. 상용 서비스에서는 “기억을 어디에 저장하고 어떻게 삭제할지”가 중요합니다.

6.4 장점

  • 제품화 관점이 가장 강함: API, session, storage, RBAC, tracing, scheduler, control plane이라는 상용 요소가 정리되어 있습니다.
  • C#과 결합이 쉬움: Python process를 별도 서비스로 띄우고 HTTP/SSE로 붙이면 됩니다.
  • 업무 도구 포장에 적합: custom function tools를 C# API proxy로 만들거나 MCP로 연결할 수 있습니다.
  • HITL 설계가 자연스러움: 위험 작업을 중간에 멈추고 사용자 승인 이벤트로 처리하는 제품 UX를 만들기 좋습니다.

6.5 단점과 리스크

  • Python 운영 부담: C# 주력 팀이라면 Python dependency, virtualenv/uv, 배포, 모니터링, 장애 대응 체계를 새로 관리해야 합니다.
  • AgentOS가 제품의 일부가 됨: 단순 라이브러리보다 서비스 운영에 가깝기 때문에 infra 설계가 필요합니다.
  • DB/Vector DB 선택: memory/knowledge를 어떻게 저장할지에 따라 비용과 latency가 크게 바뀝니다.
  • Tool 권한 설계: Agno가 구조를 제공해도 실제 권한 정책은 제품 요구사항에 맞게 직접 구현해야 합니다.

8.9 ECC와 Ruflo를 같이 쓸 때의 판단

둘 다 Claude Code 강화 계열인데 무엇이 다른가?

Payload를 문자열 객체로 계속 변환하지 말고 ReadOnlyMemory<byte> 중심으로 두면 JSON/SSE 파싱 경로에서 불필요한 allocation을 줄일 수 있습니다. UI에 표시할 때만 필요한 만큼 decode합니다.

10.3 Zero-copy / 저할당 네트워크 처리 포인트

  • System.Text.Json source generator: reflection 기반 serializer 대신 compile-time metadata 사용.
  • Utf8JsonReader: hot path에서 DOM 파싱(JsonDocument)을 남발하지 않고 streaming parse.
  • PipeReader: SSE/streaming 응답을 chunk 단위로 읽고, line/event boundary만 잘라 처리.
  • Channel<T>: agent event를 bounded channel로 흘려 backpressure를 명확히.
  • ArrayPool<byte> / MemoryPool<byte>: 대형 tool result, file diff, trace payload 처리 시 버퍼 재사용.
  • ValueTask: 동기 완료가 잦은 adapter path에서 task allocation 감소.
  • 프로세스 격리: AI agent의 memory leak/GC/의존성 문제를 C# 앱 성능 경로에서 분리.

- Do not introduce new production dependencies without explicit justification.

## Build and verification
- After modifying C# files, run:
  - dotnet build -c Release
  - dotnet test -c Release
- For performance-sensitive changes, add or update BenchmarkDotNet benchmarks.
- For public APIs, update XML docs and usage examples.

## C# performance policy
- Prefer Span<T>, ReadOnlySpan<T>, Memory<T>, ReadOnlyMemory<T> where ownership is clear.
- Prefer ArrayPool<T> or ObjectPool<T> only when lifetime and clearing rules are explicit.
- Avoid LINQ in hot paths.

- Prefer System.Text.Json source generation for stable DTOs.
- Use Utf8JsonReader/Utf8JsonWriter for zero-copy JSON parsing/writing in high-throughput paths.
- Use ValueTask only when it is measurably beneficial and API constraints are understood.
- Do not use unsafe code unless there is a benchmark and a clear safety boundary.

## Review behavior
- Before editing, state the plan and risk.
- Make minimal diffs.
- Never rewrite unrelated files.
- If tests fail, report the failing test and isolate the cause before broad refactoring.

# Dotnet Performance Review

Use this skill when reviewing C# code for performance-sensitive paths.

## Workflow
1. Identify hot paths and expected throughput/latency constraints.
2. Check for avoidable allocations:

   - closures and captures

#!/usr/bin/env python3
# .codex/hooks/pre_tool_policy.py
import json
import re
import sys

payload = json.load(sys.stdin)
tool_input = payload.get("tool_input") or {}
command = tool_input.get("command", "")

blocked_patterns = [
    r"\brm\s+-rf\s+/",
    r"\bgit\s+push\b",
    r"\bgit\s+push\s+--force\b",
    r"\bdotnet\s+nuget\s+push\b",
    r"\bsetx\s+.+TOKEN\b",
    r"\bchmod\s+-R\s+777\b",
]

for pattern in blocked_patterns:
    if re.search(pattern, command):
        print(json.dumps({
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": f"Blocked by repository policy: {pattern}"
            }
        }))
        sys.exit(0)

# No output means allow normal Codex flow.
sys.exit(0)
중요: hook은 편리한 guardrail이지만 완전한 보안 경계가 아닙니다. Codex 문서 기준으로 PreToolUse는 Bash, apply_patch, MCP tool call을 intercept할 수 있지만 모든 shell/WebSearch/비-MCP 경로를 완전히 막는 것은 아닙니다. 실제 보안은 sandbox_mode, approval_policy, network off, read-only mode, CI 격리와 함께 설계해야 합니다.

13.11 C# 제품에 Codex CLI를 붙이는 통합 구조

C# 앱에 Codex를 직접 library처럼 넣는 것보다는 프로세스 격리 + JSONL/app-server adapter 방식이 현실적입니다. C# 본체는 권한·세션·diff·audit를 통제하고, Codex는 작업 디렉터리 안에서 agent 작업을 수행하게 만듭니다.

권장 아키텍처

C# Product / IDE / Agent Workspace Terminal │ ├─ IAgentRuntime │ ├─ StartSessionAsync() │ ├─ SendPromptAsync() │ ├─ StreamEventsAsync() │ ├─ RequestApprovalAsync() │ └─ ApplyOrRejectPatchAsync() │ ├─ CodexProcessAdapter │ ├─ codex exec --json # one-shot automation │ ├─ codex app-server stdio # long-running integration │ └─ codex mcp-server # orchestration from another agent runtime │ ├─ Policy Layer │ ├─ sandbox profile │ ├─ approval policy │ ├─ command denylist/allowlist │ ├─ secret redaction │ └─ audit log │ └─ Workspace Isolation ├─ temp git worktree ├─ container or restricted user ├─ network disabled by default └─ explicit diff review before merge

C# adapter 구현 포인트

  • 프로세스 실행: System.Diagnostics.Process로 codex exec --json 또는 codex app-server --listen stdio://를 실행합니다.
  • 스트리밍 파싱: stdout/stderr JSONL은 System.Text.Json의 Utf8JsonReader 또는 source-generated context로 처리합니다.
  • zero-copy: event buffer는 ArrayPool<byte>, PipeReader, ReadOnlySequence<byte> 기반으로 파싱하면 GC 압력을 줄일 수 있습니다.
  • diff review: Codex가 수정한 파일은 즉시 merge하지 말고 git diff --name-only, git diff --stat, dotnet test 결과를 UI에 표시합니다.
  • 승인 모델: 외부 전송, publish, push, delete, credential 변경, paid API 호출은 C# host에서 별도 승인 UI를 요구합니다.
  • 격리: 초기 구현은 별도 worktree + sandbox + network off가 충분하고, 이후 Docker/Windows Sandbox/low-privilege account를 고려합니다.

13.14 Codex 적용 리스크 체크리스트

  • 중복 instructions: AGENTS.md, skill, prompt, hook additional context가 같은 규칙을 반복하면 모델이 혼란스러워집니다.
  • hook 과신: hook은 guardrail이며 sandbox를 대체하지 않습니다.
  • network/tool risk: MCP와 web search는 prompt injection 경로가 됩니다. network off를 기본으로 하세요.
  • secret leakage: shell_environment_policy로 TOKEN/SECRET/KEY 계열을 차단하세요.
  • skill bloat: ECC 전체 skills를 모두 넣지 말고 프로젝트별 curated subset을 유지하세요.
